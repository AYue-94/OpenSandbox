暂停与恢复

将沙箱状态暂停为 OCI 镜像，并在 Kubernetes 上从快照恢复。

概述

本指南说明如何在 OpenSandbox 中对 Kubernetes 后端沙箱使用暂停与恢复功能。暂停会将沙箱的根文件系统提交为 OCI 镜像并释放集群资源。恢复则从该镜像还原沙箱。

暂停与恢复做什么

行为
Pause 创建内部 SandboxSnapshot，将运行中容器的根文件系统提交为 OCI 镜像，然后静默沙箱运行时并释放 Pods / 池化分配
Resume 复用同一个 BatchSandbox，将其模板改写为最新的快照镜像，并从该镜像重建运行时
sandboxId 在 pause/resume 周期中保持稳定 — 调用方在整个沙箱生命周期内使用同一 ID
副本支持 当前仅限 BatchSandbox.spec.replicas=1。服务端创建的 Kubernetes 沙箱使用 replicas: 1；带有其它副本数的直接 CR 会被控制器的暂停入口拒绝。

关键设计原则

控制器级配置：Registry URL 与推送/拉取 Secret 配置在 Kubernetes controller manager 上，而不是 ~/.sandbox.toml。SDK 用户与 API 调用方无需修改代码即可使用 pause/resume — 只需对已有沙箱 ID 调用 pause 与 resume。

生命周期

Time ---------------------------------------------------------------->

Sandbox lifecycle:   [Running]--[Pausing]--[Paused]--[Resuming]--[Running]
                         |                     |
                  commit rootfs          rewrite template images
                  push to registry       recreate runtime from snapshot
                  release pods/alloc

状态机细节

沙箱会经历稳定状态与中间状态：

状态类型说明
Running稳定沙箱处于活动状态并处理请求
Pausing中间暂停操作进行中。快照提交通过内部 SandboxSnapshot 资源协调。
Paused稳定沙箱已暂停，最新 rootfs 快照就绪，运行时 Pods / 池化分配已释放
Resuming中间恢复操作进行中。控制器正将沙箱模板改写为最新快照镜像并重建运行时
Failed稳定操作失败（检查 reason 与 message 了解详情）

Lifecycle API 仅暴露上述粗粒度沙箱状态。要查看详细快照进度，请检查内部 SandboxSnapshot 资源：

控制器报告 Paused 之后，Pod 终止仍可能继续。可在此区间提交恢复请求；控制器会等待旧 Pod 被移除后再创建替换 Pod。带有 deletion timestamp 的 Pod 不会贡献新的运行时失败条件，包括 Kubernetes 在删除期间报告的终端退出状态。已记录在沙箱上的失败仍保持终端态，替换 Pod 的失败仍会正常报告。

  • Pending：快照请求已接受，等待解析源 Pod / 创建 commit Job
  • Committing：commit Job 正在运行并推送快照镜像
  • Succeed：快照就绪，可用于下一次恢复
  • Failed：快照创建失败

保留了什么

是否保留？
根文件系统内容✅ 是 — 提交为 OCI 镜像
环境变量✅ 是 — 来自 BatchSandbox 模板
运行中的进程 / 内存Rootfs 模式：否。可选的 QEMU-in-runc 模式：QEMU 进程与 Guest 内存会恢复；其它外层进程会重启。参见 QEMU VMState 快照。
显式卷挂载取决于卷类型
凭证保管库条目否 — 仅存储在 egress sidecar 内存中；恢复后需从可信控制面重新注入

Pause/resume 当前仅支持单副本。内部暂停快照只记录一个源 Pod 的容器镜像，不存储每副本状态，因此除非 BatchSandbox.spec.replicas=1，Kubernetes 控制器会拒绝暂停请求。

参见 凭证保管库 了解恢复后所需的凭证重新注入流程。

架构

API caller
    │ POST /v1/sandboxes/{id}/pause
    ▼
OpenSandbox Server
    │ PATCH BatchSandbox.spec.pause=true
    ▼
BatchSandbox Controller (Kubernetes)
    │ validates lifecycle state
    │ creates internal SandboxSnapshot CR
    ▼
SandboxSnapshot Controller
    │ resolves running Pod
    │ creates commit Job on the same node
    ▼
commit Job Pod (image-committer)
    │ containerd API: commit container rootfs → OCI image
    │ OCI registry resolver: push image
    ▼
SandboxSnapshot.status.phase = Succeed
    │ BatchSandbox.status.phase = Paused
    │ deletes Pods or releases pooled allocation
    ▼
Cluster resources released

--- Later: resume ---

API caller
    │ POST /v1/sandboxes/{id}/resume
    ▼
OpenSandbox Server
    │ PATCH BatchSandbox.spec.pause=false
    ▼
BatchSandbox Controller
    │ reads internal SandboxSnapshot
    │ rewrites pod template images from snapshot
    │ clears poolRef for pooled sandboxes
    │ recreates runtime Pods
    ▼
Sandbox running again with restored filesystem

前置条件

  1. 已部署 OpenSandbox 控制器的 Kubernetes 集群
  2. 集群节点（推送）与 Kubernetes API（拉取）均可访问的 OCI 兼容容器 registry
  3. 用于 registry 认证的类型为 kubernetes.io/dockerconfigjson 的 Kubernetes Secrets
  4. 已用快照 registry 与 secret flags 配置的 controller manager

控制器配置

使用快照相关 flags 配置 controller manager 部署：

- --snapshot-registry=registry.example.com/sandboxes
- --snapshot-registry-insecure=false
- --snapshot-push-secret=registry-snapshot-push-secret
- --resume-pull-secret=registry-pull-secret

配置参考

键类型默认值说明
--snapshot-registrystring""必需。OCI registry 前缀。镜像存储为 <registry>/<sandboxName>-<container>:snap-gen<N>。
--snapshot-registry-insecureboolfalse为快照推送启用不安全 registry 模式。仅用于 HTTP 或自签名的本地 registry。
--snapshot-push-secretstring""用于推送快照的 Kubernetes Secret 名称。必须是 kubernetes.io/dockerconfigjson 类型。
--image-committer-pod-template-filestring""commit Job Pod 的 PodTemplateSpec 覆盖文件路径。
--resume-pull-secretstring""注入到恢复后沙箱、用于拉取快照镜像的 Kubernetes Secret 名称。可与推送 Secret 相同。
--image-committer-imagestring"image-committer:dev"commit Jobs 使用的镜像。
--commit-job-timeoutduration"10m"commit Jobs 的超时时间。

opensandbox-controller Helm chart 现已直接暴露与快照相关的控制器值：

启动行为

服务端不再携带专用的 pause/resume 配置。缺少 registry 或 secret 设置时，会在 Kubernetes 控制器处理 SandboxSnapshot 时暴露，例如作为 SandboxSnapshot.status.conditions[type=Failed]，原因为 RegistryNotConfigured 等。

Registry 与 Secret 设置

步骤 1：准备 registry

任何 OCI 兼容的 registry 均可（Docker Hub、GitHub Container Registry、Harbor、私有 registry:2 实例等）。Registry 必须：

  • 可从集群节点到达（供 commit Job 推送）
  • 可从 Kubernetes API server / kubelet 到达（供恢复时拉镜像）

步骤 2：创建推送 Secret

kubectl create secret docker-registry registry-snapshot-push-secret \
  --docker-server=registry.example.com \
  --docker-username=<username> \
  --docker-password=<password-or-token> \
  --namespace=<sandbox-namespace>

步骤 3：创建拉取 Secret

拉取 Secret 由恢复后的 BatchSandbox Pod 用于拉取快照镜像。若凭证同时具备读写权限，可与推送 Secret 使用同一个：

kubectl create secret docker-registry registry-pull-secret \
  --docker-server=registry.example.com \
  --docker-username=<username> \
  --docker-password=<password-or-token> \
  --namespace=<sandbox-namespace>

使用私有 registry:2（开发）

在开发中使用集群内 registry:2 部署时：

# Create a registry deployment
kubectl create deployment docker-registry \
  --image=registry:2 --port=5000

kubectl expose deployment docker-registry --port=5000

# No authentication needed for internal registry
# Leave snapshot push/pull secret flags empty on the controller manager

使用指南

一旦配置好 controller manager 且服务端正在运行，pause/resume 即可通过标准 Lifecycle API 使用。无需修改 SDK。

暂停沙箱

curl -X POST http://localhost:8080/v1/sandboxes/{sandbox_id}/pause \
  -H "Content-Type: application/json"

响应：202 Accepted，空正文。

暂停是异步的。沙箱会经历：running → pausing → paused

检查暂停状态

curl http://localhost:8080/v1/sandboxes/{sandbox_id}

当 status 为 paused 时，文件系统已提交，集群资源已释放。

恢复沙箱

curl -X POST http://localhost:8080/v1/sandboxes/{sandbox_id}/resume \
  -H "Content-Type: application/json"

响应：202 Accepted，空正文。

沙箱会经历：paused → resuming → running

多次 pause/resume 周期

Pause 与 resume 可以重复。每次暂停周期会生成新的快照镜像标签（snap-gen1、snap-gen2，…）。下一次恢复始终使用最新快照。

管理员指南

控制器 RBAC

OpenSandbox 控制器为 pause/resume 需要以下 RBAC 权限（已包含在 Helm chart 与 make manifests 输出中）：

资源Verbs用途
sandboxsnapshotsget, list, watch, create, update, patch, delete管理 SandboxSnapshot CR
jobs / jobs/statusfull创建/监控 commit Jobs
secretsget在创建 commit Job 前验证推送 Secret 存在
podsget, list, watch查找用于 commit 的运行中 Pod

快照镜像命名

内部 pause/resume 快照镜像命名为：

<snapshot-registry>/<sandboxName>-<containerName>:snap-gen<N>

例如，使用 --snapshot-registry=registry.example.com/sandboxes、沙箱 my-sandbox、容器 sandbox、首次暂停：

registry.example.com/sandboxes/my-sandbox-sandbox:snap-gen1

服务端管理的公共快照使用相同的仓库布局，但标签由稳定的 snapshot-id 派生：

<snapshot-registry>/<sandboxName>-<containerName>:snap-<snapshotIdHex>

控制器通过 owner reference 区分两种模式。Pause/resume 快照由 BatchSandbox 控制器创建，并带有指向所属 BatchSandbox 的 controller ownerReference；公共快照由 Lifecycle 服务端创建，不使用该 ownerReference。

运行时兼容性

内置的 rootfs-v1 image committer 需要暴露兼容的 containerd task pause/resume 与可写快照 API 的容器运行时。handler 为 runsc 的 gVisor RuntimeClasses 目前不满足该契约。Lifecycle 服务端会在持久化快照记录或创建 SandboxSnapshot 资源之前拒绝这些工作负载的公共快照创建，使运行中的沙箱保持不变。

原生 gVisor checkpoint/restore 需要专用的快照后端，并非由 rootfs-v1 committer 提供。

Commit Job

控制器为每次暂停创建一个短生命周期的 Kubernetes Job：

  • Job 名称：<snapshotName>-commit
  • 节点亲和性：运行在与源 Pod 相同的节点上（需要访问 containerd socket）
  • 超时：10 分钟（ActiveDeadlineSeconds）
  • TTL：完成后 5 分钟（TTLSecondsAfterFinished）
  • 镜像：image-committer（可通过控制器 --image-committer-image flag 配置）

Commit Job 挂载来自源节点的主机 containerd socket，并以 UID 0 运行。这使 image-committer 镜像获得节点级容器运行时访问权限。请仅使用受信任的镜像，最好按 digest 固定，或由准入策略控制。

内置 image committer 直接使用 containerd API 进行容器查找、task pause/unpause、可写快照镜像创建以及 registry 推送。提交前，它会验证节点的 content store 是否包含该节点平台的每个基础镜像 blob，并从原始镜像 digest 拉取缺失的 blob；这可避免 CRI 在镜像解包期间丢弃压缩内容后导致快照失败。源 registry 默认使用 HTTPS。若受信任的源 registry 需要跳过 TLS 校验或使用纯 HTTP，请通过 image-committer Pod 模板向 commit 容器注入 SOURCE_IMAGE_REGISTRY_INSECURE=true。可复用的 Go 契约与默认实现见 pkg/imagecommitter；提供商专用二进制可提供凭证提供程序并复用标准 CLI 契约。Job 还保留主机 /run/containerd/fifo 挂载，以便兼容实现使用 containerd task exec。内置实现使用的任何准备命令均为尽力而为，不会改变 commit 接口。

运维可控的 Pod 模板可添加标签、注解、ServiceAccount、调度设置、init containers、sidecars，以及在必需的 commit 容器上设置资源、env、envFrom 等。模板是合并基础，控制器生成的不变量会覆盖冲突的模板值。控制器保留源 nodeName、重启策略、committer 镜像、镜像拉取策略、命令、参数、安全上下文、终止消息设置，以及必需的环境变量、挂载与卷。环境变量、挂载与卷按名称合并，冲突时必需的控制器值优先。额外的常规 sidecar 必须终止，Job 才能完成。

模板引用的任何 ServiceAccount 或准入配置必须存在于每个沙箱命名空间中。Unpause Jobs 不会收到 commit Pod 模板，因为它们不访问 registry。

若 commit Job 失败，控制器会在同一节点上创建尽力而为的 <snapshotName>-unpause Job，以解除可能因 committer 突然退出而保持暂停状态的源容器。

删除 SandboxSnapshot 会清理 Kubernetes 的 commit/unpause Jobs，但不会从 registry 删除已推送的 OCI 镜像。重复的暂停周期会创建如 snap-gen<N> 的标签；请在外部配置 registry 保留或垃圾回收策略。

监控

检查 SandboxSnapshot 状态：

kubectl get sandboxsnapshot -n <namespace>
# NAME          PHASE       SANDBOX_ID     AGE
# my-snapshot   Succeed     my-sandbox     5m

kubectl describe sandboxsnapshot my-snapshot -n <namespace>

需要关注的关键字段：

  • status.phase：Pending → Committing → Succeed / Failed
  • status.conditions：带有可读消息的就绪或失败原因
  • status.containers：每个已提交容器的镜像 URI
  • status.sourcePodName / status.sourceNodeName：解析出的快照执行源

监控沙箱状态转换

通过 Lifecycle API 检查沙箱状态时，你会看到中间状态：

暂停流程：

curl http://localhost:8080/v1/sandboxes/{sandbox_id}
# Response during pause:
{
  "id": "my-sandbox",
  "status": {
    "state": "Pausing",
    "reason": "PAUSING",
    "message": "Pausing sandbox"
  }
}

恢复流程：

curl http://localhost:8080/v1/sandboxes/{sandbox_id}
# Response during resume:
{
  "id": "my-sandbox",
  "status": {
    "state": "Resuming",

故障排查

1. 快照卡在 Failed — 找不到推送 Secret

原因：controller manager 配置的 --snapshot-push-secret 在沙箱命名空间中不存在。

解决方案：

kubectl get secret registry-snapshot-push-secret -n <namespace>
# If missing:
kubectl create secret docker-registry registry-snapshot-push-secret \
  --docker-server=<registry> \
  --docker-username=<user> \
  --docker-password=<token> \
  -n <namespace>

控制器在创建 commit Job 之前验证 Secret 是否存在（fail-fast）。Secret 创建后，触发新的暂停周期即可。

2. 快照长时间卡在 Committing

检查 commit Job 及其 Pod：

kubectl get job -n <namespace> -l sandbox.opensandbox.io/snapshot=<snapshotName>
kubectl describe pod <commit-pod-name> -n <namespace>

常见原因：

症状原因解决方案
ContainerCreating 超过 30sSecret 缺失或类型错误将 Secret 重建为 kubernetes.io/dockerconfigjson
FailedMount 事件找不到 Secret见上文问题 #1
Pod 在运行但 Job 从不完成节点无法到达 registry检查节点到 registry 的网络连通性
Pod 日志中出现 unauthorizedSecret 中的凭证错误用 kubectl get secret ... -o yaml 验证 Secret 内容

3. Secret 类型错误

Docker registry Secret 必须是类型 kubernetes.io/dockerconfigjson。通用 Secret（Opaque）会导致 FailedMount 错误。

# Check secret type
kubectl get secret registry-snapshot-push-secret -o jsonpath='{.type}'
# Expected: kubernetes.io/dockerconfigjson

# If wrong type, delete and recreate:
kubectl delete secret registry-snapshot-push-secret
kubectl create secret docker-registry registry-snapshot-push-secret \
  --docker-server=<registry> \
  --docker-username=<user> \
  --docker-password=<token>

4. Registry 不可达（超时后 Committing → Failed）

症状：Commit Job Pod 启动、运行一段时间后，因推送错误失败。

检查：

# Inspect commit Pod logs
kubectl logs <commit-pod-name> -n <namespace>

# Test registry connectivity from a node
kubectl run registry-test --rm -it --image=alpine -- \
  wget -O- https://<registry>/v2/ --timeout=5

常见原因：

  • Registry 在防火墙后，集群节点无法访问
  • 自签名 TLS 证书未被 containerd 信任
  • Registry URL 错误（http vs https）

5. 恢复已接受但运行时 Pod 无法启动

原因：无法拉取快照镜像。

kubectl describe pod <resumed-pod-name> -n <namespace>
# Look for: ErrImagePull or ImagePullBackOff

检查：

  • --resume-pull-secret 配置正确，且 Secret 存在于命名空间中
  • 拉取镜像的节点可访问 registry
  • 暂停期间快照镜像已成功推送（检查 status.containers）

6. SandboxSnapshot 未被处理（无 status）

原因：OpenSandbox 控制器未运行。

kubectl get pods -n opensandbox-system
kubectl logs -n opensandbox-system deployment/opensandbox-controller-manager

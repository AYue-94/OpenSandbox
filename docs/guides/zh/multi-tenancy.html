多租户

通过按租户 API 密钥与自动命名空间路由，在 Kubernetes 命名空间间隔离沙箱工作负载。

多租户使单次 OpenSandbox Server 部署能够服务多个独立消费者，每个消费者隔离在各自的 Kubernetes 命名空间中。每个租户获得专用 API 密钥，所有沙箱生命周期操作（创建、列表、获取、删除）都会自动限定在该租户的命名空间内。

要求

  • opensandbox-server >= 0.2.2
  • Kubernetes 运行时（在 server.toml 中 runtime.type = "kubernetes"）
  • 每个租户一个 Kubernetes 命名空间，由集群管理员预先创建
  • 默认 Helm chart RBAC（已包含具备跨命名空间访问能力的 ClusterRole）
提示

多租户模式下的代理路由
与单租户模式不同，启用多租户后代理路由需要 OPEN-SANDBOX-API-KEY。请确保客户端在代理请求中携带该请求头。

警告

不支持 Docker
多租户依赖 Kubernetes 命名空间隔离。若配置了 runtime.type = "docker" 同时又启用了租户，服务器会以致命错误拒绝启动。

工作原理

Request with OPEN-SANDBOX-API-KEY header
       │
       ├── Tenant provider configured?
       │       ├── YES → lookup key in tenant provider
       │       │       ├── found  → inject tenant context, route to tenant namespace
       │       │       └── not found → 401 Unauthorized
       │       └── NO  → validate against server.api_key (single-tenant legacy)

多租户生效时：

  1. 鉴权中间件通过已配置的 provider 将 API 密钥解析为 TenantEntry。
  2. 租户的命名空间被注入到请求作用域的 ContextVar。
  3. 沙箱生命周期操作（create/list/get/delete）使用解析得到的命名空间。
  4. 列表操作只返回已认证租户命名空间内的沙箱。
  5. 在多租户模式下，代理路由（/sandboxes/{id}/proxy/...）也需要 OPEN-SANDBOX-API-KEY。

配置

在 server.toml 中添加 [tenants] 段即可启用多租户。提供两种 provider 后端：file（本地 TOML）与 http（远程端点）。

File Provider（默认）

在 server.toml 中添加：

[tenants]
provider = "file"

然后在以下路径之一创建 tenants.toml（按顺序检查）：

  1. $SANDBOX_TENANTS_CONFIG_PATH 环境变量
  2. ~/.opensandbox/tenants.toml

示例 tenants.toml：

[[tenants]]
name = "team-alpha"
namespace = "sandbox-alpha"
api_keys = ["sk-alpha-key-1", "sk-alpha-key-2"]

[[tenants]]
name = "team-beta"
namespace = "sandbox-beta"
api_keys = ["sk-beta-key-1"]

每个租户条目需要：

字段说明
name唯一的可读租户标识
namespace目标 Kubernetes 命名空间（服务器启动时必须已存在）
api_keys该租户的一个或多个 API 密钥（支持密钥轮换）

约束：

  • API 密钥在所有租户间必须唯一（重复 → 启动错误）。
  • 每个租户至少要有一把密钥。
  • 使用 [tenants] 时必须从 server.toml 中移除 server.api_key。

HTTP Provider

适用于由外部 IAM 或租户管理系统管理租户的环境：

[tenants]
provider = "http"
endpoint = "https://iam.internal/opensandbox/tenant-lookup"
max_stale_seconds = 300.0
timeout_seconds = 5.0
auth_header = "X-Internal-Auth"
auth_token = "bearer-token-here"
字段默认值说明
provider"file""file" 或 "http"
endpoint—HTTP 必需。服务器用 GET 解析密钥的 URL。
max_stale_seconds300.0端点不可达时，最多用陈旧缓存服务多少秒。
timeout_seconds5.0HTTP 请求超时。
auth_header—可选的 provider 级鉴权请求头名称。
auth_token—该请求头的可选令牌值。

HTTP 端点约定：

请求：

GET {endpoint}
Header: OPEN-SANDBOX-API-KEY: <api_key>

响应（200）：

{
  "namespace": "sandbox-alpha",
  "ttl": 60
}

响应（401）：

{
  "code": "UNAUTHORIZED",
  "message": "Invalid API key"
}

HTTP provider 按密钥缓存结果，并使用服务器建议的 ttl。TTL 到期后同步重新拉取。若端点不可达，陈旧条目最多服务到 max_stale_seconds，之后请求以 503 失败。

警告

HTTP provider 跳过启动时命名空间校验
HTTP provider 按 API 密钥解析租户，无法在启动时枚举全部租户，因此会跳过 fail-fast 命名空间检查（改为记录警告）。file provider 会在启动时加载完整 tenants.toml，任何租户命名空间缺失或不可访问仍会 fail-fast。使用 HTTP provider 时，请在签发租户 API 密钥前确保命名空间存在且可访问。

命名空间准备

接入租户之前，集群管理员必须准备好目标命名空间。

1. 创建命名空间

kubectl create namespace sandbox-alpha

2. ResourceQuota（推荐）

apiVersion: v1
kind: ResourceQuota
metadata:
  name: tenant-quota
  namespace: sandbox-alpha
spec:
  hard:
    requests.cpu: "8"
    requests.memory: 16Gi
    limits.cpu: "16"
    limits.memory: 32Gi
    pods: "20"

配额耗尽行为

当命名空间配额耗尽时，POST /v1/sandboxes 会快速失败并返回 403 KUBERNETES::QUOTA_EXCEEDED，而不是等待沙箱创建超时后返回 KUBERNETES::POD_READY_TIMEOUT：

  • 计数配额（count/sandboxes.agents.x-k8s.io）：Kubernetes 准入会立即拒绝创建 Sandbox。
  • 计算配额（requests.cpu、requests.memory、pods）：Sandbox 会被创建，但其 Pod 无法准入；一旦控制器记录到工作负载状态中的拒绝（ReconcilerError），服务器会尽快暴露该结果（通常在一秒内）。

响应体使用标准 ErrorResponse 形状，message 携带 Kubernetes 准入细节，例如 exceeded quota: tenant-quota, requested: requests.cpu=1, used: requests.cpu=8, limited: requests.cpu=8。SDK 客户端会将其呈现为 HTTP 状态 403 的类型化错误。提高配额或释放容量后重试即可——无需重启服务器。

该 fail-fast 约定目前适用于 agent-sandbox 工作负载供应商（[kubernetes] workload_provider = "agent-sandbox"）。在默认的 batchsandbox 供应商下，控制器尚未把准入拒绝传播到 CR 状态，因此配额耗尽仍会等待沙箱创建超时并返回 KUBERNETES::POD_READY_TIMEOUT。

3. LimitRange（推荐）

apiVersion: v1
kind: LimitRange
metadata:
  name: tenant-limits
  namespace: sandbox-alpha
spec:
  limits:
  - default:
      cpu: "1"
      memory: 2Gi
    defaultRequest:
      cpu: 250m
      memory: 512Mi
    type: Container

Container 默认值会作用于每个省略对应资源设置的容器，包括 OpenSandbox egress sidecar。请在生命周期服务器中为 sidecar 配置更小的专用值，以免 egress 容器继承为沙箱工作负载准备的默认值。

4. Egress sidecar 资源（推荐）

在服务器的 [egress] 配置中加入 Kubernetes 资源设置：

[egress]
image = "opensandbox/egress:v1.1.7"
requests = { cpu = "25m", memory = "64Mi" }
limits = { cpu = "250m", memory = "256Mi" }

requests 与 limits 可独立配置。这些值是基础 DNS/nft 强制执行的起点；请对工作负载做基准测试，在使用凭证保管库或透明 mitmproxy 时留出更多余量。若你的 LimitRange 定义了最小值，egress 设置必须满足它们。

5. 服务器 RBAC

默认 Helm chart（opensandbox-server）已部署带跨命名空间访问能力的 ClusterRole + ClusterRoleBinding。多租户无需额外 RBAC 变更——服务器 ServiceAccount 已可在任意命名空间中操作。

热重载

File provider

file provider 监视 tenants.toml 的变更（每 2 秒轮询）。变更无需重启服务器即可生效：

  • 新增密钥 → 下一个请求立即有效。
  • 移除密钥 → 立即无效（401）。
  • 重载时解析错误 → 保留上一份配置，并记录警告。
  • 文件被删除 → 所有租户密钥失效。

监视器会监听父目录，以处理 Kubernetes ConfigMap 的原子符号链接替换。

HTTP provider

无需显式重载——缓存条目按各自 ttl 过期，并在下次查找时重新拉取。

密钥轮换

多租户特意支持每个租户多把 API 密钥，以实现零停机密钥轮换：

  1. 将新密钥加入 tenants.toml（或通过 HTTP provider 签发）。
  2. 等待热重载（file）或 TTL 过期（HTTP）。
  3. 将客户端更新为使用新密钥。
  4. 从配置中移除旧密钥。

过渡窗口内新旧密钥同时有效。

从单租户迁移

  1. 为租户创建目标命名空间。
  2. 编写 tenants.toml，将现有 API 密钥作为租户条目，指向现有命名空间： 
    [[tenants]]
name = "default"
namespace = "your-existing-namespace"
api_keys = ["your-existing-api-key"]
  3. 在 server.toml 中添加 [tenants] 段： 
    [tenants]
provider = "file"
  4. 从 server.toml 的 [server] 中移除 api_key。
  5. 部署。现有密钥继续可用，现已成为租户密钥。
  6. 按需添加更多租户。

回滚：从 server.toml 移除 [tenants] 段，恢复 server.api_key，然后重启。

隔离模型

服务器本身不强制资源配额或网络策略。隔离委托给 Kubernetes：

维度Kubernetes 机制范围
Resource quotaResourceQuota按命名空间的 CPU、内存、存储
Default limitsLimitRange按命名空间的默认容器资源
Network isolationEgress sidecar通过 egress 代理实现按沙箱的出站策略
Sandbox countResourceQuota（pod count）按命名空间的 Pod 上限
RBACRoleBinding按命名空间的 API 访问
说明

Pool API 不按租户隔离
Pool 管理路由（/pools）当前在服务器配置的默认命名空间中操作，而不是已认证租户的命名空间。Pool 是共享资源。若需要按租户隔离 Pool，请创建独立的服务器部署，或等待未来的按租户 Pool 支持。

故障排查

现象原因处理
服务器启动退出："Multi-tenancy requires Kubernetes namespaces" 配置了 runtime.type = "docker" 与 [tenants] 改用 Kubernetes 运行时，或移除 [tenants]
服务器退出："Remove server.api_key from server.toml" 同时存在 server.api_key 与 [tenants] 从 [server] 段移除 api_key
服务器退出：namespace not found 租户命名空间不存在 启动服务器前执行 kubectl create namespace <ns>
配置变更后有效密钥仍 401 热重载尚未生效 等待 2s（file）或 TTL 秒数（HTTP）
503 TENANT_PROVIDER_UNAVAILABLE HTTP 端点不可达，且缓存已超过 max_stale_seconds 修复端点连通性；增大 max_stale_seconds
启动时报 Duplicate api_key 错误 同一密钥分配给多个租户 确保每把密钥在所有租户间唯一

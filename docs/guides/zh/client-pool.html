客户端 Pool

SDK 侧沙箱池如何工作、如何配置，以及各受支持 SDK 的最小示例。

OpenSandbox SDK 提供实验性的客户端沙箱池（client-side sandbox pool）：在服务端预热一小缓冲的就绪沙箱，使 acquire() 能快速返回，而不必在热路径上承担完整的沙箱创建延迟。

适用于 Python（async 与 sync）、JavaScript/TypeScript、Kotlin/Java 与 Go。C# 目前尚未提供客户端 pool。

警告：实验性

客户端 pool API 标记为实验性，可能在次要版本之间变更。若在生产中依赖它，请固定 SDK 版本。

实际池化的是什么

pool 不会池化 SDK 的 Sandbox 对象。它池化的是在 OpenSandbox 服务端上已预热、就绪沙箱的 ID。

适合需要反复获取全新沙箱、对延迟敏感的 worker。pool 保持远端沙箱就绪；它与 HTTP 连接池是分开的。借出的沙箱仍会消耗服务端资源，必须显式清理。

两条流程并发进行：

  • Warmup（仅 leader）。每个节点上都会运行后台 reconcile 循环。持有 primary lock 的节点计算空闲缺口并补齐。Python、JavaScript 与 Kotlin 使用名义上一秒的节奏，并且每个完成的 tick 最多接纳 warmup_create_qps 次新创建。Kotlin 按固定速率调度；若上一次 reconcile 仍在运行，JavaScript 会跳过一个 tick；Python 在上一个 tick 完成后等待一秒。Go 使用可配置的 reconcile_interval，并用 warmup_concurrency 限制每个 tick。成功的 warmup 会独立发布到空闲缓冲，TTL 为 idle_timeout。
  • Acquire（任意节点）。acquire() 从 store 弹出一个空闲 ID，为其连接一个 Sandbox 客户端，可选运行健康检查与到调用方超时的 renew()，然后交给调用方。非 leader 节点可自由 acquire；仅补齐与收缩由 leader lock 门控。

空闲成员关系携带沙箱 ID 及其过期时间，从不携带 HTTP 连接或客户端侧 Sandbox 对象。状态 store 还协调 leader 租约、共享空闲目标与 TTL，以及命名空间销毁围栏（fence）。基于 Redis 的 store 使该协调与空闲成员关系在进程与 Pod 之间可见。

warmup 路径——上文仅 leader 的补齐流程——值得放大，因为它是 pool 中唯一由分布式锁门控的部分：

生命周期模型

在优雅运行期间，每个 pool 实例经历 NOT_STARTED → STARTING → RUNNING → DRAINING → STOPPED。启动失败或非优雅关闭可直接进入 STOPPED。健康状态单独跟踪为 HEALTHY | DEGRADED | DRAINING | STOPPED；在连续 degraded_threshold 次 warmup 或 reconcile 失败后，pool 进入 DEGRADED。Go 在降级时对补齐应用指数退避。Python、JavaScript 与 Kotlin 继续按名义上一秒的节奏尝试 reconcile：warmup_create_qps 是其压力控制，而 snapshot().backoff_active / snapshot().backoffActive 仅为兼容性保留，且始终为 false。调用方无需直接观察这些状态——snapshot() 为诊断暴露它们。

Python、JavaScript 与 Kotlin 的内置 warmup 创建只发起一次生命周期请求。Python 与 Kotlin 对 HTTP 429、其他可重试状态以及传输恢复禁用连接级重试策略；JavaScript 的生命周期传输不会自动重试。没有 pool 级的 Retry-After 节流。自定义 PooledSandboxCreator 通过 PooledSandboxCreateContext.connection_config 或 createConnectionConfig 接收 warmup 连接配置，必须遵守它，并遵守 skipHealthCheck，以保持分阶段行为。失败的创建会被记录，后续 tick 可能接纳替换工作。普通独立创建与 AcquirePolicy.DIRECT_CREATE 保留其通常的传输行为。

没有 release()

沙箱是短暂的。一旦调用了 acquire()，沙箱就归你所有，直到你 destroy() / kill() 它。max_idle 约束的是预热缓冲，而不是应用代码借出的沙箱数量，也不是 DIRECT_CREATE 回退产生的沙箱数量。

在 Python 的 SandboxPoolAsync 中，所有权在 acquire() 返回时转移。若调用在连接或创建沙箱之后失败或取消，pool 会尝试 kill 该沙箱并在传播错误前关闭其本地资源。在续约或最终 pool 状态检查期间取消（包括清理期间的重复取消）不会跳过该清理。一旦获取成功，调用方仍负责处置。

空缓冲行为：AcquirePolicy

全部四个 pool SDK 都暴露这些策略。Acquire 会消费一个候选；它不会等待未来的 warmup 工作填满空缓冲。

策略尝试的空闲候选数候选耗尽时
FAIL_FAST 最多一个 返回 pool-empty/acquire 错误
DIRECT_CREATE（默认） 最多一个 创建全新沙箱
RETRY_NEXT_IDLE 最多 max_acquire_retries 个 返回 pool-empty/acquire 错误
RETRY_NEXT_IDLE_THEN_CREATE 最多 max_acquire_retries 个 创建全新沙箱

max_acquire_retries / maxAcquireRetries / MaxAcquireRetries 默认为 3。它约束的是候选尝试总数，而不是第一次之后再额外重试三次。每个候选都可能消耗 acquire 就绪预算；直接创建会增加其自身的启动延迟。

start() 开始后台补齐，不会等待缓冲填满。启动期间使用 DIRECT_CREATE，或在使用 FAIL_FAST 前观察空闲计数。pool 不是并发上限：直接创建与已借出的沙箱可以超过 max_idle。

分阶段 Warmup

分阶段 warmup 将创建接纳与创建后工作分开：

  1. 在每个 reconcile tick，leader 最多接纳 min(max_idle - idle - warming, warmup_create_qps) 次创建。生命周期 create 请求只尝试一次，并返回一个不运行其正常内联就绪循环的客户端。创建执行上限是内部的，解析为 ceil(warmup_create_qps * 1.5)，因此缓慢创建不会使活跃创建工作无限增长。自定义 creator 必须遵守其 PooledSandboxCreateContext 提供的 warmup 连接配置与 skipHealthCheck。
  2. 已创建的沙箱进入延迟阶段队列。首次就绪检查在 warmup_health_check_initial_delay 之后运行；失败按 warmup_health_check_polling_interval 重试，直到 warmup_ready_timeout，包括在截止时间的最后一次检查。
  3. warmup_sandbox_preparer 运行一次。若已配置，则 warmup_post_prepare_health_check 随后以相同轮询间隔重试，直到 warmup_post_prepare_health_check_timeout；重试从不重跑 preparer。
  4. 健康的沙箱被续约并提交到空闲缓冲。warmup_concurrency 限制活跃的创建后工作。不成功的就绪轮询之间的延迟不会永久占用全部容量。

Python、JavaScript 或 Kotlin 没有 reconcile_interval 设置，也没有补齐退避。对于使用过旧设置的 Python/Kotlin 配置，请移除 reconcile_interval=... / reconcileInterval(...)，用 warmup_create_qps / warmupCreateQps(...) 控制创建接纳，并用 warmup_concurrency / warmupConcurrency(...) 仅控制创建后容量。

warmup_create_qps 是接纳上限，而非完成率保证。创建延迟、就绪、准备、状态 store 延迟、事件循环或执行器容量，以及延迟/跳过的 reconcile tick，都可能降低观察到的 warmup 吞吐。

选择状态 Store

  • InMemoryPoolStateStore — 仅单进程。适合开发、测试与单实例 worker。对 gunicorn/uvicorn worker、Celery 或 Kubernetes 副本不是进程级共享。
  • 基于 Redis 的 store（RedisPoolStateStore、AsyncRedisPoolStateStore、JVM 上的 sandbox-pool-redis、Go 中的 poolredis、JavaScript 中的 @alibaba-group/opensandbox/pool-redis）— 多进程或多 Pod 部署必需。同一逻辑 pool 的所有节点必须共享相同的 pool_name 与 Redis key_prefix，且每个进程必须使用唯一的 owner_id。

适用于每次部署的规则

  • max_idle 仅约束预热缓冲。它不限制借出的沙箱或 DIRECT_CREATE 回退。
  • 共享同一 pool 的所有节点必须使用相同的创建与 warmup 定义。若该定义变更，请在新的 pool_name（或 Redis key_prefix）下滚动发布，并退役旧的（见下文「退役旧的 pool 命名空间」）。不要试图把变更后的模板重新填入同一 pool_name：release_all_idle() 不会围栏其他节点、不会降低 max_idle，也不会阻止任何当前 leader（可能仍在运行旧代码）在滚动部署期间立即把旧模板沙箱 ID 重新发布到共享缓冲。
  • resize(max_idle) 与 release_all_idle() 可从任意节点调用。
  • 将 primary_lock_ttl 配置为高于 warmup_ready_timeout 加上预期 preparer 时间与运维余量。SDK 会独立续约领导权并为每次提交设围栏，但丢失租约会导致进行中的 warmup 被丢弃而非发布。

最小用法

Python（sync）

from datetime import timedelta

from opensandbox import (
    AcquirePolicy,
    InMemoryPoolStateStore,
    PoolCreationSpec,
    SandboxPoolSync,
)
from opensandbox.config import ConnectionConfigSync

pool = SandboxPoolSync(
    pool_name="demo-pool",
    owner_id="worker-1",
    max_idle=2,
    state_store=InMemoryPoolStateStore(),
    connection_config=ConnectionConfigSync(domain="api.opensandbox.io"),
    creation_spec=PoolCreationSpec(image="ubuntu:22.04"),
    warmup_create_qps=10,
    warmup_concurrency=128,
)

pool.start()
try:
    sandbox = pool.acquire(
        sandbox_timeout=timedelta(minutes=30),
        policy=AcquirePolicy.DIRECT_CREATE,
    )
    try:
        result = sandbox.commands.run("echo pool-ok")
        print(result.logs.stdout[0].text)
    finally:
        sandbox.destroy()
finally:
    pool.shutdown(graceful=True)

from datetime import timedelta

    try:

    return err

    return err

诊断与运维

每个 pool SDK 暴露这些操作（名称遵循语言约定）：

  • snapshot() — pool 阶段、健康状态、计数器（空闲大小、进行中 warmup、连续失败、最后错误）。
  • snapshot_idle_entries() — 当前空闲沙箱 ID 及其过期时间戳。
  • resize(max_idle) — 在运行时更改目标缓冲大小。
  • release_all_idle() — 排空当前可见的空闲缓冲并尽力 kill 每一项，而不停止 pool。适用于在短暂上游问题后强制一批新的 warmup。它不会更改 max_idle，不会围栏其他节点，也不会阻止活跃 leader 立即补齐——因此它不是在同一 pool_name 上交换创建模板的安全方式。对于那种情况，请在新的 pool_name 下退役整个命名空间（见下文）。

现有清理方法保留其原始执行行为。若需可选的有界并行清理，请使用 Python 的 release_all_idle_parallel(max_workers=50)、Kotlin 的 releaseAllIdle(concurrency)、JavaScript 的 releaseAllIdle(concurrency)，或 Go 的具体方法 (*DefaultSandboxPool).ReleaseAllIdleParallel(ctx, maxWorkers)。这些方法会校验正的并发值，并等待每个已排空的 ID 收到尽力 kill 尝试。Go 方法有意放在 SandboxPool 接口之外，以保持与第三方实现者的兼容性。

追踪 Warmup

Python、JavaScript 与 Kotlin/Java 发出可选的 OpenTelemetry warmup span。在 Python 中设置 enable_tracing=True，或在 JavaScript/JVM 连接配置中设置 enableTracing: true / .enableTracing(true)。应用提供其 OpenTelemetry provider 与 exporter。阶段名称与语言特定属性参见 SDK Tracing。

Pool shutdown 停止该本地 pool 实例；它不会终止已交给调用方的沙箱。要退役共享命名空间，请使用下方的 manager。

退役旧的 Pool 命名空间

每个受支持的 pool SDK 都暴露带有 destroy 操作的 SandboxPoolManager，应用相同的 DESTROYING → DESTROYED 协议：

  1. 向状态 store 写入 DESTROYING 围栏，使任何仍在运行的对等实例看到它并停止补齐，而不是与退役竞争。
  2. 尽力排空并 kill 每个空闲沙箱，受 drain 超时约束。
  3. 清除持久的每 pool 状态。
  4. 写入带 tombstone TTL（默认 7 天）的 DESTROYED 墓碑，使未来调用方不能静默重新绑定到同一 pool_name。

Destroy 是幂等的：在已墓碑化的命名空间上调用它会报告 DESTROYED，而不会排空或 kill 任何内容。若 drain 或清理无法完成，命名空间保持 DESTROYING，调用报告 destroy 未完成；重试是安全的，会从中断处继续。

Python / Kotlin — SandboxPoolManager.destroy(poolName, options)，通过 PoolDestroyOptions（strategy、drain_timeout、tombstone_ttl）配置。

JavaScript — SandboxPoolManager.create({ stateStore, connectionConfig })，然后 await manager.destroy(poolName, options)。

Go — (*SandboxPoolManager).Destroy(ctx, poolName, options)：

manager, err := opensandbox.NewSandboxPoolManagerBuilder().
    StateStore(store).
    ConnectionConfig(connCfg).
    Build()
if err != nil {
    return err
}

result, err := manager.Destroy(ctx, "orders-v2", opensandbox.PoolDestroyOptions{})
if err != nil {
    return err
}
log.Printf("retired %s: drained=%d killed=%d",
    result.PoolName, result.DrainedIdleCount, result.KilledIdleCount)

PoolDestroyOptions 与其他 SDK 镜像对应。Strategy 选择算法，目前仅实现 PoolDestroyForce。DrainTimeout 与 TombstoneTTL 是 *time.Duration：保持为 nil 使用默认值（30s 与 7 天），或设置显式零值以在无截止时间的情况下 drain，并写入永不过期的墓碑。

围栏使退役在不必先停止每个写入者的情况下保持安全，并在两个层面强制执行。状态 store 会以 *PoolDestroyedError 拒绝 PutIdle、SetMaxIdle 与 SetIdleEntryTTL，且不发放 primary lock，从而停止补齐。pool 本身也会在启动时、每次 acquire 之前、acquire 持有存活沙箱之后，以及每个 reconcile tick 上检查围栏：幸存的对等方在下一个 tick 上直接停止；进行中的 acquire 会失败，而不是通过 direct-create 回退向已退役命名空间铸造新沙箱；在围栏落地前刚取得的沙箱会被 kill 而不是交出。acquire 后检查很重要，因为空闲取出有意不设围栏，以便 destroy 可以排空：一旦 ID 被取出，destroy 无法再触及它，因此 acquire 必须自行处置。针对已墓碑化的 PoolName 启动新 pool 会因同样原因失败，因此重新绑定该名称需要等待墓碑 TTL 过期，或轮换到新的 PoolName。

一个有意的例外：若状态 store 本身不可达，destroy 状态不可知，因此已在 store 故障时回退到直接创建的策略（DIRECT_CREATE、RETRY_NEXT_IDLE_THEN_CREATE）会假定 ACTIVE 并继续，与现有的 try_take_idle 故障行为一致。FAIL_FAST 与 RETRY_NEXT_IDLE 则暴露故障。该放宽止于已从空闲缓冲取出的沙箱：那里的检查是失败关闭的，不可达 store 意味着沙箱被 kill，因为没有其他东西再跟踪它。

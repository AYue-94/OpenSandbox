Egress Mitmproxy：大型 SSE 分块尾部截断

为何在 HTTP/1.1 上游以 TCP RST 关闭连接时，大型 SSE 响应体会被截断；如何确认，以及如何在网关侧修复。

现象

沙箱经 egress sidecar 调用 LLM API 时，有时会收到被截断的 SSE 流：大于约 1 MB 的 data: 事件会在接近末尾处被切断，SDK 报告 JSON 畸形或连接中断。丢失的数据量不等（从几字节到数百 KB）。

根因

对整条数据路径的字节级仪器化表明，这是标准的 TCP RST 语义，而非 mitmproxy 或 OpenSandbox 的缺陷：

  1. 上游在接收缓冲区中仍有未读数据时关闭连接（例如网关流式返回响应却未消费客户端请求体）。内核会发送 TCP RST，而不是干净的 FIN。
  2. 根据 RFC 793，RST 会丢弃接收端内核接收缓冲区中尚未读取的数据——响应尾部未读部分在任何应用代码看到之前就已丢失。
  3. 随后 mitmproxy 的 h11 解析器硬错误（incomplete chunked read），该 flow 被终止，客户端连接被关闭。

已通过受控的 A/B/C 实验确认（同一服务端代码、负载、代理与客户端；仅关闭行为不同）：

关闭行为 mitmproxy TCP 特征 客户端结果
A. 关闭时仍有未读请求数据 → 内核 RST ConnectionResetError 截断，5/5
B. 请求已消费后关闭 → 干净 FIN 干净 EOF 完整，5/5
C. 请求已消费 + SO_LINGER=0 强制 RST（接收缓冲区为空） ConnectionResetError 截断，4/5

单元 C 是铁证：仅 RST 即可复现截断，即使没有未读数据；FIN 则从不如此。直接慢读客户端在面对服务端 A 时会丢失整个响应体，面对服务端 B 则无丢失，因此损失量纯粹取决于 RST 到达时尾部还有多少未读数据。HTTP/2 上游与 keep-alive 连接不受影响。

复现

components/egress/tests/mitm-sse-truncation/ 中的脚本会驱动本地 mitmdump（选项与 egress 透明模式相同），对接一个以 RST 关闭的合成 SSE 上游：

cd components/egress
./tests/mitm-sse-truncation/run.sh            # reproduce the truncation (TLS, 4 MiB, RST close)
./tests/mitm-sse-truncation/run.sh --plain     # controls that must pass
./tests/mitm-sse-truncation/run.sh --delay-close 1
./tests/mitm-sse-truncation/run.sh --read-request
./tests/mitm-sse-truncation/run.sh --probe --keep-workdir   # show the error hook in the mitmdump log

需要 python3、openssl、mitmdump（若不在 PATH 上，可传 --mitmdump PATH）。选项：--size、--iterations、--delay-close、--plain、--read-request、--probe、--mitmdump、--port、--upstream-port、--workdir、--keep-workdir。

修复（网关侧）

mitmproxy 或 OpenSandbox 中没有可写的代码修复——这些字节已从内核中消失。修复应落在上游服务器。

先确认是否为 RST（在网关上或前方复现时运行）：

tcpdump -ni any 'tcp port 443 and tcp[tcpflags] & (tcp-rst) != 0'   # RST right after the last response byte, no FIN
netstat -s | grep -i reset
# from a client: "Recv failure: Connection reset by peer" / curl: (56) instead of a clean EOF

然后修复关闭行为——规则是：关闭前消费请求；对 SSE，最好根本不要关闭：

  • nginx：保持 lingering_close on（默认），配合 lingering_time 30s / lingering_timeout 5s；尤其在设置了 proxy_request_buffering off 时需检查。
  • FastAPI / uvicorn / Starlette：在流式返回前读取请求体（await request.body()），否则「流式响应后关闭」可能使请求体未读 → RST。
  • Go net/http：显式排空请求体（io.Copy(io.Discard, r.Body)）；Go 不会替你排空。切勿在流式响应上使用 SO_LINGER 0（SetLinger(0)）。
  • 通用：优先 keep-alive（以 0\r\n\r\n 结束分块响应体）；若必须关闭，先排空接收缓冲区；HTTP/2 连接可避免整类失败。

若无法修改网关：让沙箱经 HTTP/2 访问该网关，或在其前方加一层会消费请求体并以 keep-alive 转发的代理。

状态

  • OpenSandbox 跟踪：opensandbox-group/OpenSandbox#1461 — 等待现场确认。

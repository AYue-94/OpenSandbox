QEMU VMState 快照

为 runc 沙箱内运行的 QEMU 配置并操作进程级暂停与恢复。

本页目录
  1. 状态与制品模型
  2. 准备 QEMU 工作负载镜像
  3. 暂停与恢复流程
  4. 使用 Helm 做生产部署
  5. 验证
  6. 故障排查

本指南说明如何准备、部署并验证支持进程级暂停与恢复的 QEMU-in-runc 工作负载。该工作负载在普通 runc 容器内运行 QEMU，并不使用虚拟化的 Kubernetes RuntimeClass。

此模式仍为实验性。它会恢复 QEMU Guest 内存、vCPU 以及可迁移设备状态。外层 runc 容器中的其他进程会从 BatchSandbox Pod 模板重新启动。

初始的 qemu-v1 实现支持同一 BatchSandbox 的暂停与恢复。公开的快照克隆 API 尚不能恢复 QEMU VMState，因为其快照记录不会持久化完整的 Pod 模板与 QEMU 启动计划。独立的公开快照操作在发布制品后会恢复其源 VM。

状态与制品模型

状态存储
外层容器 rootfs既有的 rootfs 快照镜像
可写 Guest qcow2 overlayRootfs 快照镜像；overlay 不得位于 Kubernetes volume mount 之下
Guest RAM、vCPU 与模拟设备状态包含 zstd 压缩 QEMU migration stream 的 VMState 镜像
不可变 Guest 基础镜像原始镜像层，或可独立获取的只读卷
PVC、hostPath、云盘、网络对端状态OpenSandbox 不会复制

两类镜像都会被推送到已配置的镜像 Registry，并以 manifest digest 记录在同一份 SandboxSnapshot.status 中。恢复从不依赖可变 tag。

准备 QEMU 工作负载镜像

QEMU 支持是工作负载镜像与 OpenSandbox 之间的约定。镜像必须：

  1. 使用 QMP Unix socket 启动 QEMU；
  2. 根据生效的 QEMU 设置生成 OpenSandbox launch manifest；
  3. 将 v1 捕获的每个可写 Guest overlay 保留在容器 rootfs 中；
  4. 识别 OpenSandbox 恢复环境，并为 QEMU 添加 -incoming；
  5. 仅在 QMP socket 与 Guest 服务可用后才变为 Ready。

声明 Pod 模板约定

在创建 QEMU 容器的 Pod 模板上设置以下 annotations。对于独立沙箱，使用 BatchSandbox.spec.template.metadata。对于池化沙箱，使用 Pool.spec.template.metadata，以便分配出的 Pod 携带该约定。

annotations:
  sandbox.opensandbox.io/checkpoint-provider: qemu
  sandbox.opensandbox.io/qemu-container: qemu
  sandbox.opensandbox.io/qemu-qmp-socket: /run/qemu/qmp.sock
  sandbox.opensandbox.io/qemu-launch-manifest: /run/qemu/launch.json
  # Optional: constrain restore to compatible nodes.
  sandbox.opensandbox.io/qemu-required-node-class: shenlong-v1
Annotation是否必需用途
checkpoint-provider是选择 qemu provider。OpenSandbox 不会扫描进程名。
qemu-container是命名拥有 QEMU、QMP 与 launch manifest 的 Pod 容器。
qemu-qmp-socket是该容器内 QMP Unix socket 的干净绝对路径。
qemu-launch-manifest是该容器内 OpenSandbox launch manifest 的干净绝对路径。
qemu-required-node-class否将恢复限制到带有匹配 OpenSandbox QEMU node-class 标签的节点。

这些路径是容器内路径。它们不需要挂载进 controller Pod。snapshot worker 通过节点上的容器运行时到达目标容器。

生成 OpenSandbox launch manifest

Launch manifest 由 OpenSandbox 定义。它不是原生 QEMU 文件，QEMU 也不会自动创建它。工作负载镜像维护者必须在 Pod 变为 Ready 之前生成该文件。

在容器 entrypoint 中，用与构建 QEMU 命令相同的生效值生成该文件。当 CPU、内存、磁盘或设备可能通过环境变量或 Pod 模板变化时，不要把静态文件烘焙进 Docker 镜像。

Launch manifest 示例：

{
  "formatVersion": "qemu-v1",
  "architecture": "amd64",
  "qemuVersion": "6.2.0",
  "machineType": "pc-q35-6.2",
  "cpuModel": "host",
  "vcpus": 2,
  "memoryBytes": 536870912,
  "qemuConfigDigest": "sha256:...",
  "disks": [
    {
      "id": "osdisk",
      "overlayPath": "/vm/state.qcow2",
      "capture": "rootfs"
    }
  ]
}
字段含义
formatVersion必须为 qemu-v1。
architectureQEMU 使用的 Guest 主机架构，例如 amd64。
qemuVersion运行中 QEMU 进程报告的版本。Worker 会通过 QMP 校验该值。
machineType显式带版本的 machine type，例如 pc-q35-6.2。
cpuModel生效的 QEMU CPU model。host 通常要求恢复节点同构。
vcpus生效的 vCPU 数量。
memoryBytes生效的 Guest RAM 大小（字节）。
qemuConfigDigest由工作负载生成的、对兼容性敏感的 QEMU 配置的 SHA-256 标识。
disks可写 overlay 及其捕获策略。v1 仅支持 capture: rootfs。

qemuConfigDigest 在 v1 中是不透明的兼容性值。请从 machine、CPU、内存、firmware、磁盘、网络与设备设置的规范表示确定性计算它。排除 PID、时间戳、QMP 路径、生成的 socket 名等瞬时值。OpenSandbox 会记录该 digest，但不会据此重建 QEMU 命令行。

以原子方式写入 manifest，避免并发快照读到不完整的 JSON：

runtime_dir=/run/qemu
manifest_tmp="$runtime_dir/launch.json.tmp"
manifest="$runtime_dir/launch.json"

mkdir -p "$runtime_dir"
cat >"$manifest_tmp" <<EOF
{
  "formatVersion": "qemu-v1",
  "architecture": "amd64",
  "qemuVersion": "$qemu_version",
  "machineType": "$machine_type",
  "cpuModel": "$cpu_model",
  "vcpus": $vcpus,
  "memoryBytes": $memory_bytes,
  "qemuConfigDigest": "$qemu_config_digest",
  "disks": [
    {"id":"osdisk","overlayPath":"/vm/state.qcow2","capture":"rootfs"}
  ]
}
EOF
mv "$manifest_tmp" "$manifest"

参考 E2E entrypoint 展示了如何用同一组变量构建 manifest 与 QEMU 参数。参见 reference entrypoint。

暴露 QMP 并支持恢复

在 QEMU 启动时创建已声明的 QMP Unix socket：

qemu_args+=(
  -qmp "unix:/run/qemu/qmp.sock,server=on,wait=off"
)

QMP 控制存活的 QEMU 进程，并传输 migration stream。Launch manifest 则单独声明兼容性与磁盘捕获意图，这些信息无法仅靠 QMP 可靠恢复。

工作负载 entrypoint 必须检测 OPENSANDBOX_RESTORE_MODE=qemu-v1，并用 OPENSANDBOX_VMSTATE_DIR 中提供的 loader stream 启动 QEMU：

if [[ "${OPENSANDBOX_RESTORE_MODE:-}" == "qemu-v1" ]]; then
  test -x "$OPENSANDBOX_VMSTATE_DIR/vmstate-loader"
  qemu_args+=(
    -incoming
    "exec:$OPENSANDBOX_VMSTATE_DIR/vmstate-loader stream --dir $OPENSANDBOX_VMSTATE_DIR"
  )
fi

OpenSandbox 注入恢复目录与 loader；完整 QEMU 命令行仍由工作负载拥有。它必须在消费 incoming stream 之前重建相同的 machine、CPU、内存、firmware、磁盘、网络与设备拓扑。

将可写 overlay 保留在 rootfs 中

每个声明为 capture: rootfs 的磁盘都必须是 QEMU 容器可写 rootfs 中的文件。它不得解析到 Kubernetes volumeMount 或 volumeDevice 之下，包括 PVC、hostPath、projected volume 或 emptyDir。nerdctl commit 不会捕获这些挂载，snapshot worker 会拒绝该配置，而不是创建不完整的快照。

不可变基础镜像可以来自原始镜像层，或其他可独立获取的只读来源。现有的用户 init containers 会在注入的 VMState loader 之前再次运行，因此它们必须幂等，且不得覆盖已恢复的可写 overlay。

暂停与恢复流程

  1. Controller 解析带注解的 QEMU 容器，并在同一节点上调度 snapshot Job。
  2. Worker 校验每个声明为 capture: rootfs 的可写 overlay 都不在容器的 Kubernetes volume mount 路径之下。
  3. Worker 使用 QMP migration 导出 VM 状态，用 zstd 压缩，并放入标准容器镜像。
  4. QEMU 进入 post-migration 状态后，worker 冻结外层容器，提交其 root filesystem，并推送两类镜像。
  5. Controller 原子发布 rootfs 与 VMState 的 manifest digests，然后删除源 Pod。
  6. 恢复时，loader init container 在 emptyDir 中还原并校验 VMState 文件。它会被追加到所有用户 init containers 之后。
  7. 重建的 QEMU 容器消费 migration stream。其他外层容器进程按 Pod 模板正常启动。

不会使用 savevm。它会创建与 qcow2 存储耦合的内部快照，不是此处所用的 live Guest RAM 传输方式。

使用 Helm 做生产部署

没有 QEMU 专用的 Helm 功能开关。Helm 安装的是集群级快照能力；每个 BatchSandbox 或 Pool 的 Pod 模板通过上述 annotations 自行启用。仅 rootfs 的工作负载继续使用既有行为。

前置条件

  • Linux 节点向 QEMU 容器暴露 /dev/kvm。
  • 镜像 Registry 必须接受 Docker schema 2 或 OCI image manifests，并且 snapshot Jobs 与 kubelet/containerd 都能访问。
  • 恢复时，QEMU 版本、带版本的 machine type、CPU model、vCPU 数量、RAM 大小、设备配置 digest，以及可选的 node class 必须匹配。
  • Snapshot Job 需要主机 containerd runtime 目录、主机 PID namespace 以及 SYS_PTRACE。由于它控制 containerd socket，已经运行在节点级信任边界内。Pod Security 与 admission 策略必须显式允许该 Job。
  • VMState 可能包含来自 Guest RAM 的凭证与用户数据。请按敏感持久化存储同等标准应用访问控制、加密、保留与删除策略。
  • 根据实测压缩载荷大小规划 Registry 容量。压缩效果取决于 Guest 内存内容，不保证一定很小。

Controller 镜像与 image-committer 镜像都必须来自支持 qemu-v1 的版本。尤其不要依赖较旧 chart 对 controller.snapshot.imageCommitterImage 的默认值；请显式覆盖。

创建 Registry 凭证

Commit Job 与恢复后的 Pod 运行在沙箱命名空间中，因此引用的 Secrets 必须存在于每个使用快照与恢复的命名空间：

kubectl -n sandbox-team create secret docker-registry snapshot-registry \
  --docker-server=registry.example.com \
  --docker-username='<username>' \
  --docker-password='<password-or-token>'

当凭证具备 push、image-committer pull 与 resume pull 三项权限时，可共用一个 Secret。生产部署可在每个沙箱命名空间中使用同名、最小权限分离的 Secrets。

配置并安装 chart

创建 values 文件：

controller:
  image:
    repository: registry.example.com/opensandbox/controller
    tag: qemu-v1
  snapshot:
    imageCommitterImage: registry.example.com/opensandbox/image-committer:qemu-v1
    containerdSocketPath: /var/run/containerd/containerd.sock
    commitJobTimeout: 15m
    registry: registry.example.com/opensandbox-snapshots
    registryInsecure: false
    snapshotPushSecret: snapshot-registry
    imageCommitterPullSecret: snapshot-registry
    resumePullSecret: snapshot-registry

安装或升级 controller。在全新集群上，请先安装 base chart——controller chart 不再附带 CRD：

helm upgrade --install base ./manifests/charts/base

helm upgrade --install opensandbox-controller \
  ./manifests/charts/controller \
  --namespace opensandbox-system \
  --create-namespace \
  --values qemu-snapshot-values.yaml

将 CRD 同步进 base chart（make -C manifests helm-gen-crds），并升级 base，使更新后的 SandboxSnapshot CRD 生效。在创建工作负载前验证已部署能力：

kubectl -n opensandbox-system rollout status \
  deployment/opensandbox-controller-manager
kubectl -n opensandbox-system get deployment,pod
kubectl get crd sandboxsnapshots.sandbox.opensandbox.io
kubectl get crd sandboxsnapshots.sandbox.opensandbox.io \
  -o jsonpath='{.spec.versions[0].schema.openAPIV3Schema.properties.status.properties.virtualMachine.type}{"\n"}'

确认集群 admission 允许受节点信任的 snapshot Job。QEMU 模式需要主机 PID namespace、SYS_PTRACE 以及主机 containerd runtime 目录。QEMU 工作负载本身需要 /dev/kvm，除非平台提供更窄的设备权限，否则通常以特权方式运行。

对于异构集群，给兼容的恢复节点打标签，并在工作负载上声明匹配的 class：

kubectl label node <node> \
  sandbox.opensandbox.io/qemu-node-class=shenlong-v1
metadata:
  annotations:
    sandbox.opensandbox.io/qemu-required-node-class: shenlong-v1

快照镜像名会生成在已配置的 Registry 前缀之下。QEMU 沙箱会生成普通容器 rootfs 镜像（如 <prefix>/<sandbox>-<container>:<tag>）以及 VMState 镜像（如 <prefix>/<sandbox>-vmstate:<tag>）。恢复会解析并使用它们不可变的 manifest digests。

验证

专用 E2E 会从 Pool 分配一个预热的 QEMU-in-runc Pod，分别向匿名 mmap、原始 Guest 磁盘与外层 rootfs 写入独立值，快照两类镜像，并恢复为独立 Pod。它会验证 Pool 补位与脱离、不可变的 rootfs 与 VMState 镜像 digests、loader 完成、快照清理、全部三个值、Guest boot ID，以及 live counter：

cd kubernetes
make test-e2e-qemu

测试需要 Linux amd64、Docker、Kind、kubectl 与 /dev/kvm。默认会在 Kind 集群中部署隔离的 registry:2 Pod。设置 QEMU_E2E_SNAPSHOT_REGISTRY 与 QEMU_E2E_DOCKER_CONFIG 可对外部认证 Registry 验证同一流程；两个仓库为 <prefix>/qemu-rootfs 与 <prefix>/qemu-vmstate。设置 KEEP_QEMU_E2E_CLUSTER=true 可保留专用 Kind 集群以便诊断。全部覆盖项见 E2E README。

可复用的 Kind 验证环境

E2E harness 可以构建镜像、创建启用 KVM 的专用 Kind 集群、部署 controller 与 Registry、运行参考 Pool 流程，并留下环境供人工检查：

cd kubernetes
KEEP_QEMU_E2E_CLUSTER=true make test-e2e-qemu

得到的 context 为 kind-opensandbox-qemu-vmstate-e2e。Controller 运行在 opensandbox-system，集群内 registry:2 Pod 与自动化测试对象运行在 qemu-vmstate-e2e：

kubectl --context kind-opensandbox-qemu-vmstate-e2e \
  -n opensandbox-system get deploy,pod
kubectl --context kind-opensandbox-qemu-vmstate-e2e \
  -n qemu-vmstate-e2e get pod,service,pool,batchsandbox

若要改用外部认证 Registry，请提供其仓库前缀与本地 Docker config.json；harness 会创建临时 Kubernetes pull/push Secret，且不会打印其内容：

QEMU_E2E_SNAPSHOT_REGISTRY=registry.example.com/team \
QEMU_E2E_DOCKER_CONFIG=/path/to/config.json \
KEEP_QEMU_E2E_CLUSTER=true \
make test-e2e-qemu

下面的命令使用独立的 qemu-manual 命名空间，因此不必先删除保留下来的 E2E 对象。

演示 Guest 在同一 PID 1 进程中运行 HTTP 服务与可变内存映射。QEMU 用户态网络会把外层容器 loopback 端口 18080 转发到 Guest 端口 8080；该服务不会暴露在 Pod IP 上。

Endpoint用途
GET /healthz验证恢复后的 Guest 进程正在提供请求
PUT /value在进程内存映射中存储最多 512 字节的值
GET /value读取当前内存映射值
GET /status读取 PID、Guest boot ID、基于 mmap 的 live counter，以及 value
PUT /disk在原始可写 Guest 磁盘中存储标记
GET /disk读取原始 Guest 磁盘标记

定义阶段等待函数，并在 Guest 内存、Guest 磁盘与外层容器 rootfs 中写入三个独立标记：

wait_for_sandbox_phase() {
  local wanted=$1
  local phase=
  for _ in $(seq 1 180); do
    phase=$(kubectl --context "$OSB_QEMU_CONTEXT" \
      -n "$OSB_QEMU_NAMESPACE" get batchsandbox "$OSB_QEMU_SANDBOX" \
      -o jsonpath='{.status.phase}' 2>/dev/null || true)
    if [[ "$phase" == "$wanted" ]]; then
      return 0
    fi
    sleep 2
  done
  echo "timed out waiting for phase=$wanted; last phase=$phase" >&2
  return 1
}

export OSB_MEMORY_TOKEN="MANUAL-MMAP-$(date -u +%Y%m%dT%H%M%SZ)"
export OSB_DISK_TOKEN="MANUAL-DISK-$(date -u +%Y%m%dT%H%M%SZ)"
export OSB_ROOTFS_TOKEN="MANUAL-ROOTFS-$(date -u +%Y%m%dT%H%M%SZ)"

kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_QEMU_POD" -c qemu -- \
  curl --fail --silent --show-error --request PUT \
  --data-binary "$OSB_MEMORY_TOKEN" http://127.0.0.1:18080/value
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_QEMU_POD" -c qemu -- \
  curl --fail --silent --show-error --request PUT \
  --data-binary "$OSB_DISK_TOKEN" http://127.0.0.1:18080/disk
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_QEMU_POD" -c qemu -- sh -c \
  'mkdir -p /var/lib/opensandbox && printf "%s" "$1" > /var/lib/opensandbox/rootfs-marker' \
  sh "$OSB_ROOTFS_TOKEN"

OSB_BEFORE=$(kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_QEMU_POD" -c qemu -- \
  curl --fail --silent --show-error http://127.0.0.1:18080/status)
OSB_SOURCE_UID=$(kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  get pod "$OSB_QEMU_POD" -o jsonpath='{.metadata.uid}')
printf 'before: %s\nsource uid: %s\n' "$OSB_BEFORE" "$OSB_SOURCE_UID"

kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \

export OSB_SNAPSHOT_NAME="$OSB_QEMU_SANDBOX-pause"
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \

kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  wait --for=delete pod/"$OSB_QEMU_POD" --timeout=120s

快照必须报告 status.format: qemu-v1、status.containers 下的 rootfs 镜像 digest，以及 status.virtualMachine 下不同的 VMState 镜像 digest 与非零压缩大小。

将 spec.pause 编辑为 false 以恢复，然后验证进程级连续性与两层文件系统：

kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  edit batchsandbox "$OSB_QEMU_SANDBOX"
wait_for_sandbox_phase Succeed
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  wait --for=condition=Ready pod/"$OSB_QEMU_POD" --timeout=180s

OSB_AFTER=$(kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_QEMU_POD" -c qemu -- \
  curl --fail --silent --show-error http://127.0.0.1:18080/status)
OSB_AFTER_DISK=$(kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_QEMU_POD" -c qemu -- \
  curl --fail --silent --show-error http://127.0.0.1:18080/disk)
OSB_AFTER_ROOTFS=$(kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_QEMU_POD" -c qemu -- cat /var/lib/opensandbox/rootfs-marker)
OSB_RESTORED_UID=$(kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  get pod "$OSB_QEMU_POD" -o jsonpath='{.metadata.uid}')

OSB_BEFORE_BOOT_ID=$(printf '%s\n' "$OSB_BEFORE" | sed -n 's/.*"boot_id":"\([^"]*\)".*/\1/p')
OSB_AFTER_BOOT_ID=$(printf '%s\n' "$OSB_AFTER" | sed -n 's/.*"boot_id":"\([^"]*\)".*/\1/p')
OSB_BEFORE_COUNTER=$(printf '%s\n' "$OSB_BEFORE" | sed -n 's/.*"counter":\([0-9]*\).*/\1/p')
OSB_AFTER_COUNTER=$(printf '%s\n' "$OSB_AFTER" | sed -n 's/.*"counter":\([0-9]*\).*/\1/p')

[[ "$OSB_SOURCE_UID" != "$OSB_RESTORED_UID" ]]
[[ "$OSB_BEFORE_BOOT_ID" == "$OSB_AFTER_BOOT_ID" ]]
((OSB_AFTER_COUNTER > OSB_BEFORE_COUNTER))
[[ "$OSB_AFTER" == *"\"value\":\"$OSB_MEMORY_TOKEN\""* ]]
[[ "$OSB_AFTER_DISK" == *"\"value\":\"$OSB_DISK_TOKEN\""* ]]
[[ "$OSB_AFTER_ROOTFS" == "$OSB_ROOTFS_TOKEN" ]]

printf 'after: %s\ndisk: %s\nrootfs: %s\nrestored uid: %s\n' \
  "$OSB_AFTER" "$OSB_AFTER_DISK" "$OSB_AFTER_ROOTFS" "$OSB_RESTORED_UID"
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  get pod "$OSB_QEMU_POD" -o jsonpath='{range .status.initContainerStatuses[*]}{.name}{"="}{.state.terminated.reason}{"\n"}{end}'

所有断言都必须返回零。Pod UID 必须变化，Guest boot ID 必须保持不变，live counter 必须增加，三个 token 都必须匹配，且 VMState loader init container 必须报告 Completed。成功恢复后，内部 SandboxSnapshot 会被删除。结束时只删除测试对象；Kind 基础设施仍然可用：

kubectl --context "$OSB_QEMU_CONTEXT" delete \
  -f kubernetes/config/samples/alibaba/qemu-vmstate/standalone.yaml

使用 Pool 进行手工验证

先创建 Pool 并等待其预热 QEMU Pod。然后创建分配该 Pod 的 BatchSandbox：

kubectl --context "$OSB_QEMU_CONTEXT" apply \
  -f kubernetes/config/samples/alibaba/qemu-vmstate/pool.yaml
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  get pool qemu-pool -w

在 Pool 报告 ready capacity 后停止 watch，并运行：

kubectl --context "$OSB_QEMU_CONTEXT" apply \
  -f kubernetes/config/samples/alibaba/qemu-vmstate/pooled-sandbox.yaml
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  get batchsandbox qemu-pooled -w

从 allocation annotation 读取已分配的 Pod 名，并写入与独立场景相同的三个标记：

export OSB_POOLED_POD=$(kubectl --context "$OSB_QEMU_CONTEXT" \
  -n "$OSB_QEMU_NAMESPACE" get batchsandbox qemu-pooled \
  -o jsonpath='{.metadata.annotations.sandbox\.opensandbox\.io/alloc-status}' \
  | jq -r '.pods[0]')

export OSB_POOL_MEMORY_TOKEN="POOL-MMAP-$(date -u +%Y%m%dT%H%M%SZ)"
export OSB_POOL_DISK_TOKEN="POOL-DISK-$(date -u +%Y%m%dT%H%M%SZ)"
export OSB_POOL_ROOTFS_TOKEN="POOL-ROOTFS-$(date -u +%Y%m%dT%H%M%SZ)"

kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_POOLED_POD" -c qemu -- \
  curl --fail --silent --show-error --request PUT \
  --data-binary "$OSB_POOL_MEMORY_TOKEN" http://127.0.0.1:18080/value
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_POOLED_POD" -c qemu -- \
  curl --fail --silent --show-error --request PUT \
  --data-binary "$OSB_POOL_DISK_TOKEN" http://127.0.0.1:18080/disk
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  exec "$OSB_POOLED_POD" -c qemu -- sh -c \
  'mkdir -p /var/lib/opensandbox && printf "%s" "$1" > /var/lib/opensandbox/rootfs-marker' \
  sh "$OSB_POOL_ROOTFS_TOKEN"

运行 kubectl edit batchsandbox qemu-pooled -n qemu-manual 并添加 spec.pause: true。暂停成功后，验证 Pool 特有的交接：

kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  get batchsandbox qemu-pooled \
  -o jsonpath='phase={.status.phase}{" poolRef="}{.spec.poolRef}{" templateContainers="}{.spec.template.spec.containers[*].name}{"\n"}'
kubectl --context "$OSB_QEMU_CONTEXT" -n "$OSB_QEMU_NAMESPACE" \
  get sandboxsnapshot qemu-pooled-pause -o yaml

阶段必须为 Paused。Controller 会将已分配 Pod 的模板物化进 BatchSandbox，并清除 spec.poolRef；这种脱离是有意的，因此恢复会创建独立 Pod，而不是退回 Pool。将 spec.pause 改回 false，等待 qemu-pooled-0 变为 Ready，然后对其调用 GET /status、GET /disk 以及 rootfs 标记检查。

清理 Pool 示例，但不删除 Kind 集群：

kubectl --context "$OSB_QEMU_CONTEXT" delete \
  -f kubernetes/config/samples/alibaba/qemu-vmstate/pooled-sandbox.yaml
kubectl --context "$OSB_QEMU_CONTEXT" delete \
  -f kubernetes/config/samples/alibaba/qemu-vmstate/pool.yaml

故障排查

现象检查项
InvalidCheckpointContract确认四个必需 annotations 都在实际 Pod 模板上，并指向存在的容器。路径必须干净且为绝对路径。
Launch manifest 复制或解码失败进入注解容器，读取确切路径，确认 entrypoint 在 readiness 成功前写入完整 JSON。
QMP probe 失败确认声明路径是 Unix socket，且 QEMU 使用 server=on,wait=off。检查是否有 supervisor 删除或替换了 socket。
QEMU 版本不匹配比较 manifest 中的 qemuVersion 与运行中二进制。在容器启动时生成 manifest，而不是把过期版本烘焙进镜像。
可写磁盘被拒绝检查 QEMU 容器上的每个 volumeMount 与 volumeDevice。capture: rootfs overlay 不能位于任何挂载路径之下。
Snapshot Job 被 admission 拒绝允许 image-committer Job 身份在具备快照能力的节点上使用主机 PID、SYS_PTRACE 与主机 containerd runtime 目录。
Snapshot Job ImagePullBackOff确认 imageCommitterPullSecret 存在于沙箱命名空间，并能拉取已配置的 image-committer 镜像。
恢复后的 Pod ImagePullBackOff确认 resumePullSecret 存在于沙箱命名空间，并能拉取 rootfs 与 VMState 镜像仓库。
QEMU 在消费 -incoming 时退出将 QEMU 版本、machine type、CPU model、vCPU 数量、内存、firmware、磁盘、网络与设备拓扑与捕获的兼容性数据对比。
恢复后 Pod 无法调度检查 /dev/kvm、节点亲和性，以及 qemu-required-node-class 与节点 qemu-node-class 标签是否匹配。

从快照状态与 commit Job 日志开始诊断：

kubectl -n <namespace> get sandboxsnapshot <name> -o yaml
kubectl -n <namespace> get job,pod \
  -l sandbox.opensandbox.io/sandbox-snapshot-name=<name>
kubectl -n <namespace> logs job/<commit-job-name> --all-containers

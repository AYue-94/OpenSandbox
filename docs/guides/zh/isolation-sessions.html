隔离会话

在沙箱内通过 bubblewrap 隔离的按次执行 bash 会话，用于快速、受控的代码运行。

要求

本指南所涉功能需要的组件版本：

  • execd >= 1.0.20 提供基础隔离会话支持；>= 1.0.21 推荐，以获得 binds、List sessions、uid_mode: "userns"，以及默认可写白名单（/workspace、/mnt、/media、/data）
  • opensandbox-server >= 0.2.1 — 当 execd 镜像声明 bootstrap.execd.isolation 时，服务端会注入 CAP_SYS_ADMIN、apparmor=unconfined，以及 bwrap 所需的 tmpfs 挂载
  • Python SDK >= 0.1.14（isolation.run_once / isolation.session 上下文管理器）；仅生成 isolation 客户端时 >= 0.1.13 即可
  • JavaScript / TypeScript SDK >= 0.1.10（isolation.runOnce / isolation.withSession）
  • Kotlin / Java SDK >= 1.0.16（isolation.runOnce() / isolation.withSession { ... }）；仅生成 isolation 客户端时 >= 1.0.15 即可
  • C# SDK >= 0.1.4（RunOnceAsync / WithSessionAsync）
  • Go SDK >= 1.0.4（IsolationRunOnce / IsolationWithSession）

/capabilities 上的 setpriv_available / userns_available 字段是在 execd v1.0.21 之后加入的；撰文时仅 main 分支上的 execd 构建包含它们。较旧的 execd 会省略这两个字段（客户端必须容忍其缺失）。

主机要求（bwrap 二进制、CAP_SYS_ADMIN、overlayfs 等）见 服务端配置 → 主机要求。

已发布的 execd 镜像包含会话启动时使用的 fail-closed 原生 workload gate。若从 Linux 源码构建，make build 需要 C 编译器与静态 libc，并产出 bin/opensandbox-session-gate；启动 execd 前请先运行 make build-session-gate，再执行 sudo make install-session-gate，将辅助程序安装到 /opt/opensandbox/opensandbox-session-gate。请保持该路径及其父目录由 root 拥有，且不可被 group 或 world 写入。

概述

概念边界启动开销典型用途
隔离会话 单个沙箱内的 bubblewrap 命名空间 创建约 100 ms；在已有会话中后续 run 开销接近零 大量短生命周期、相互隔离的任务复用同一长生命周期会话
Bash 会话（/session） bash 进程，无额外命名空间 毫秒级 交互式 REPL 风格的命令序列
沙箱 容器或 Pod 数百毫秒到数秒 租户、工作区或用户边界
安全运行时（gVisor / Kata） 每个沙箱的用户态内核或虚拟机 10–500 ms 硬件级防护，抵御容器逃逸
会话创建 vs. 每次 run 的开销

创建会话大约需要 100 ms，因为 execd 在启动 bwrap 后会短暂等待，以检测立即退出的子进程。会话一旦存在，每次 POST /run 都会复用同一个 bash 进程，因此单次 run 的开销可忽略不计。设计负载时应把创建成本摊销到同一会话中的多次 run 调用上。

适合场景：RL rollouts、批量代码评分、多工具 agent 运行 — 每个 worker 一个沙箱，内部再跑大量隔离任务。

不适合：跨语言 kernel（请用 /code）、交互式 REPL（请用 /session），或需要硬信任边界抵御内核漏洞利用（请用 gVisor / Kata；参见 安全容器运行时）。

工作原理

execd 为每个会话 fork 一个 bwrap 子进程；bwrap 设置 Linux 命名空间，然后在其中 exec 一个长生命周期的 bash。

图中未展示的两点：

  • bash 是长生命周期的，因此一次 run 中的 export X=1 对同一会话中的下一次 run 可见（绝不会对另一会话可见）。
  • FS 代理从命名空间外部读写合并后的工作区视图，因此即使 bash 正忙，上传与下载仍可工作。

run 请求流程

非成功路径：

事件发生什么
Run 的 timeout_seconds 到期 execd 取消该 run 上下文，向 bwrap 进程组发送 SIGINT，并发出 IsolatedError SSE 事件；会话本身保持存活。
bwrap 进程已退出 下一次 run 返回带有 session process has exited 的 IsolatedError SSE 事件；只有 ErrContextNotFound（会话 ID 未知）会变成 HTTP 级错误。需 DELETE 后重建。
空闲超时到达 GC 执行与 DELETE 相同的拆除逻辑。
客户端在 SSE 中途断开 Gin 请求上下文被取消，execd 向正在运行的命令发送 SIGINT；该 run 不会在后台继续执行。

快速开始

curl

# Probe.
curl -s http://localhost:44772/v1/isolated/capabilities

# Create.
SESSION=$(curl -s -X POST http://localhost:44772/v1/isolated/session \
  -H "Content-Type: application/json" \
  -d '{
    "profile": "strict",
    "workspace": {"path": "/workspace", "mode": "overlay"},
    "idle_timeout_seconds": 300
  }' | jq -r .session_id)

# Run (SSE: stdout / error / complete).
curl -N -X POST "http://localhost:44772/v1/isolated/session/$SESSION/run" \
  -H "Content-Type: application/json" \
  -d '{"code": "export X=1; echo $X", "timeout_seconds": 30}'

# Second run reuses shell state.
curl -N -X POST "http://localhost:44772/v1/isolated/session/$SESSION/run" \
  -H "Content-Type: application/json" \
  -d '{"code": "echo $X"}'  # prints 1

# Delete.
curl -X DELETE "http://localhost:44772/v1/isolated/session/$SESSION"

Python SDK

from opensandbox import Sandbox
from opensandbox.models.isolated import (
    CreateIsolatedSessionRequest, IsolatedWorkspaceSpec, IsolatedRunOpts,
)

# Sandbox.create is an async classmethod, so await it before entering
# the async context manager.
async with (await Sandbox.create("python:3.11")) as sandbox:
    # One-shot.
    await sandbox.isolation.run_once(
        "python -c 'print(42)'", workspace="/workspace", profile="strict",
    )

    # Persistent session.
    async with sandbox.isolation.session(
        CreateIsolatedSessionRequest(
            workspace=IsolatedWorkspaceSpec(path="/workspace", mode="overlay"),
            profile="strict",
            idle_timeout_seconds=300,
        )
    ) as session:
        await session.run("export STAGE=train")
        await session.run("python train.py", opts=IsolatedRunOpts(timeout_seconds=600))
        await session.files.write_file("/workspace/data.csv", data_bytes)

    # Reattach after a client restart.
    handle = await sandbox.isolation.attach(known_session_id)

会话生命周期

位于 execd 的 /v1/isolated/ 下。当 execd 配置了访问令牌时，请使用 X-EXECD-ACCESS-TOKEN。

方法路径用途
POST/session创建；返回 {session_id, created_at}。
GET/sessions列出活动会话。
GET/session/{id}完整状态；回显创建参数，便于无状态客户端重建句柄。
POST/session/{id}/run前台（默认）：SSE 流 stdout / error / complete。后台（"background": true）：返回 202 与 run 句柄。同一会话上的 run 会串行化。
GET/session/{id}/runs/{runId}后台 run 状态：running、exit_code、error、时间戳。
GET/session/{id}/runs/{runId}/logs后台 run 的合并输出（纯文本），支持字节游标分页。
DELETE/session/{id}销毁。
GET/capabilities能力探测。

idle_timeout_seconds > 0 会自动销毁空闲会话；设为 0 可禁用空闲 GC，并始终显式 DELETE。

后台运行

后台 run 在会话内以分离方式启动代码并立即返回；run 的合并 stdout/stderr 与退出码由 execd 捕获，客户端可在会话继续执行其他工作的同时轮询它们。

# Start detached; 202 returns {"session_id", "run_id", "started_at"}.
RUN=$(curl -s -X POST "http://localhost:44772/v1/isolated/session/$SESSION/run" \
  -H "Content-Type: application/json" \
  -d '{"code": "sleep 5 && echo done", "background": true}' | jq -r .run_id)

# Poll status until running=false.
curl -s "http://localhost:44772/v1/isolated/session/$SESSION/runs/$RUN"

# Read output (plain text). The response header EXECD-ISOLATED-TAIL-CURSOR
# carries the next byte offset for incremental reads.
curl -s "http://localhost:44772/v1/isolated/session/$SESSION/runs/$RUN/logs"
curl -s "http://localhost:44772/v1/isolated/session/$SESSION/runs/$RUN/logs?cursor=123"

Python SDK：

session = await sandbox.isolation.create(CreateIsolatedSessionRequest(
    workspace=IsolatedWorkspaceSpec(path="/workspace", mode="rw"),
))

run = await session.run_background("sleep 5 && echo done")
while (status := await session.run_status(run.run_id)).running:
    await asyncio.sleep(0.2)
print(status.exit_code)
logs = await session.run_logs(run.run_id)   # .text + .cursor for pagination

后台 run 语义：

  • timeout_seconds 仅适用于前台；后台 run 不受时间限制。
  • 后台 run 处于活动状态时，空闲 GC 会暂停；结束后恢复正常空闲窗口。删除会话会终止该 run。
  • 后台 run 需要可写的日志位置，因此只读（ro）工作区的会话会以 400 拒绝；rw 与 overlay 工作区受支持。
  • Run 与会话共享同一进程组，因此会话级信号（例如前台 run 超时或取消时发送的 SIGINT）也会送达它们。
  • 每次 logs 请求最多返回 16 MiB；对大输出请用返回的游标分页。每个 run 的日志保留上限为 16 MiB — 超出部分在 run 完成时丢弃，因此若需要超过第一页的内容，请在 run 活跃时增量拉取。
  • 若会话在 run 进行中死亡，会报告 running: false 且 error: "session terminated"；会话被删除或垃圾回收时，run 记录及其日志会被移除。

工作区模式

模式语义
rw读写绑定挂载；写入会持久化到主机。
overlay（默认）通过 overlayfs 写时复制；写入进入每会话的 upper 目录，并在 DELETE 时消失。
ro只读绑定挂载；写入会以 EROFS 失败。

Overlay 的 upper 目录位于 upper_root 下（默认 /var/lib/execd/isolation）。

由于隔离会话状态仅存在于 execd 内存中，execd 退出时留在 upper_root 下的每个 upper 目录都会成为孤儿。启动时 execd 会回收 upper_root 下残留的会话目录 — 会话状态从不会跨重启存活，因此不会丢失合法数据。只会删除具有 execd 会话布局（<id>/upper）的目录；若 upper_root 指向与其它数据共享的目录，无关子项绝不会被触碰（upper_root 仍应是专用目录）。尚无法删除的残留 — 例如仍被上一生命周期挂载引用的 upper — 会计入 upper_max_bytes，并由空闲收集器重试。在池化 / 预置沙箱中，这也能防止一名占用者的会话数据泄漏给下一名。

{ "workspace": { "path": "/workspace", "mode": "overlay" } }

绑定挂载与白名单

  • extra_writable — 以相同路径读写绑定挂载的路径（source == destination）。
  • binds — 显式 source → dest 映射，可选 readonly。source 必须已存在；dest 必须已在命名空间内存在（请将其烘焙进沙箱镜像）。
{
  "workspace": { "path": "/workspace", "mode": "rw" },
  "extra_writable": ["/data/scratch"],
  "binds": [
    { "source": "/data/in",  "dest": "/mnt/in",  "readonly": true },
    { "source": "/data/out", "dest": "/mnt/out" }
  ]
}

每个 source 在符号链接解析之后对照运维配置的 allowed_writable 白名单检查，因此符号链接无法逃逸白名单。默认白名单：/workspace、/mnt、/media、/data（允许子路径）。空白名单会拒绝所有额外绑定。

配置档与默认值

profile 字段当前仅控制命名空间内如何暴露 /tmp：

配置档/tmp
strict（默认）私有 tmpfs（--tmpfs /tmp）
balanced与沙箱共享（--bind /tmp /tmp）

workspace.mode 与 env_passthrough 独立于配置档：省略时，无论选择哪个配置档，execd 都会将 workspace.mode 规范化为 overlay，将 env_passthrough.mode 规范化为 deny。若需要持久的工作区写入（"rw"）或主机环境透传（"allow"），请显式设置这些字段。

环境变量、UID 与网络

  • env_passthrough — mode: "allow" + keys 白名单主机环境变量；默认 deny。每次 run 的覆盖放在 IsolatedRunRequest.envs。
  • uid / gid 配合 uid_mode: "setpriv"（默认，真实 setuid/setgid 降权）或 "userns"（用户命名空间重映射）。请求某种模式前，请先通过 /capabilities 检查 setpriv_available / userns_available。
  • share_net: true 共享沙箱的网络命名空间。沙箱级 egress 与凭证保管库策略仍然生效。
  • share_net: false 创建私有网络命名空间。在释放 workload 启动门控之前，execd 会打开已认证的 NetNS，用 NS_GET_USERNS 取得其真实拥有的 UserNS，并将二者绑定固定到 /run/execd/namespaces/<opaque-id>/ 下。任何校验或固定失败都会中止会话创建。execd 会在启动失败、进程退出、显式删除、空闲回收以及 runner 关闭时尝试清理固定；可重试的失败会保留会话所有权，并在 execd 存活期间重试。这适用于两种 UID 模式；加固的网络后端将要求 uid_mode: "userns"。

本阶段遗留默认行为不变：省略 share_net 仍会共享沙箱网络命名空间。仅命名空间固定本身并不会启用会话的 egress 或 ingress。

私有会话无法在 execd 重启后恢复。启用它们的部署必须将 execd 视为沙箱关键组件，并在 execd 退出时重建整个沙箱/容器；不得在仍存活的挂载命名空间内启动替换的 execd。销毁沙箱/容器会拆除该挂载命名空间并释放所有固定。execd 有意在启动时不扫描并接管不透明的命名空间固定目录，因为它们没有持久的沙箱世代信息，这样做可能卸载另一存活进程的资源。

能力探测

curl -s http://localhost:44772/v1/isolated/capabilities
{
  "available": true,
  "isolator": "bwrap",
  "version": "0.9.0",
  "setpriv_available": true,
  "userns_available": false,
  "commit_supported": false,
  "diff_supported": false
}
  • available: false — 可信原生 workload gate 缺失或不可信、缺少 bubblewrap，或主机无法创建所需命名空间（缺少 CAP_SYS_ADMIN、受限的 user-ns sysctl 等）。
  • setpriv_available / userns_available — 是否可创建 uid_mode: "setpriv" 或 "userns" 的会话。setpriv_available 仅反映 execd 的默认 UID/GID；请求不同 UID/GID 的会话在身份切换不可用时仍可能返回 503 NOT_SUPPORTED。
  • commit_supported / diff_supported — 第二阶段占位，目前返回 503。

服务端配置

将 execd 指向可选的 TOML 文件：

Flag环境变量
--isolation-configEXECD_ISOLATION_CONFIG
 
# Parent directory for per-session overlay upper dirs.
upper_root = "/var/lib/execd/isolation"

# Allocation-time threshold for total overlay upper-directory size (bytes).
# Existing sessions can write beyond this value.
# Default: 8 GiB. Set to 0 to disable the allocation check.
upper_max_bytes = 8589934592  # 8 GiB

# Sources allowed for extra_writable / binds (symlink-resolved).
# Default: ["/workspace", "/mnt", "/media", "/data"]. Empty = reject all.
allowed_writable = ["/workspace", "/mnt", "/media", "/data"]

示例：components/execd/configs/isolation.example.toml。

upper_max_bytes 在创建 overlay 工作区（默认模式）时检查。若成功的用量扫描报告总量达到或超过配置的正数限制，新会话会被拒绝。该设置不会限制已有会话的写入，也不适用于 rw 或 ro 工作区。

删除 overlay 会话并在其清理成功、总用量降到阈值以下后，可恢复准入。删除会丢弃该会话的私有 upper 数据，因此删除前请保留所需数据。

主机要求： execd 镜像中的 bwrap 与可信原生 workload gate；CAP_SYS_ADMIN（以及用于 uid_mode: "userns" 的 kernel.unprivileged_userns_clone=1）；内核中的 overlayfs（用于 overlay 工作区）。已发布镜像会自动安装 gate。Linux 源码构建必须在启动 execd 前，从 components/execd 运行 make build-session-gate，再执行 sudo make install-session-gate。

注意：当原生 workload gate 无法作为可信可执行文件打开，或 bwrap 本身无法启动（缺少二进制或缺少命名空间能力）时，/capabilities 会报告 available: false。缺少 overlayfs 不会翻转 available — overlay 探测仅影响第二阶段的 commit/diff 支持，而此类主机上默认 overlay 模式的会话创建仍可能在运行时失败。若依赖 workspace.mode: "overlay"，请直接在主机上验证 overlayfs 支持。

限制

  • diff / commit 是第二阶段占位，目前返回 503。
  • 无硬件级保证。仅有命名空间 + seccomp；若需抵御内核漏洞利用，请搭配安全运行时。
  • 仅 Linux。非 Linux 构建返回 available: false。
  • 每会话串行 run — 需要并行时请创建多个会话。
  • 绑定目标必须预先存在于沙箱镜像中。

凭证保管库

为沙箱出站请求安全注入凭证，而不把密钥暴露给工作负载。

Credential Vault 是 OpenSandbox 面向沙箱内智能体与开发者工具的出站凭证代理。真实凭证由宿主机侧 SDK 写入 egress sidecar，沙箱进程本身只拿到假值或空值。当 Claude Code、Git、curl、包管理器或模型 API 客户端发起被允许的出站 HTTPS 请求时，sidecar 会按 Credential Vault 绑定进行匹配，并在出站路径上注入所需的认证头。这样现有工具可保持原有工作流，同时真实密钥不会出现在沙箱环境变量、命令行、文件系统和日志中，从而降低提示注入或不信任代码导致的凭证外泄风险。

要求

  • opensandbox-server >= 0.2.0
  • egress >= 1.1.1
  • Python SDK >= 0.1.11
  • JavaScript/TypeScript SDK >= 0.1.9
  • Kotlin SDK >= 1.0.13
  • Go SDK >= 1.0.3
  • C# SDK >= 0.1.3
  • 服务端配置设置了 [egress].image。
  • 服务端配置设置了 [egress].mode = "dns+nft"。Credential Vault 在纯 DNS 模式下拒绝启用，因为直连 IP 可以绕过 DNS 策略。
  • 创建沙箱的请求包含出站网络策略。
  • 出站网络策略应使用 defaultAction="deny"，并显式允许每个凭证绑定所引用的主机。暂时仍兼容 default-allow，但会发出安全警告。
  • 创建沙箱的请求启用了 Credential Proxy。
  • 沙箱 Pod 未在同一网络命名空间中额外运行透明服务网格 sidecar（例如 Istio/Envoy 注入）。Credential Vault 当前假定 OpenSandbox egress sidecar 是 Pod 内唯一的透明出站拦截层。
  • 沙箱镜像包含你要运行的工具。对于 Claude Code，请使用带有 Node.js 与 npm 的镜像，例如 OpenSandbox code-interpreter 镜像。
警告：迁移说明

Credential Proxy 仍要求服务端 [egress].mode = "dns+nft"；无法提供 nft 强制执行的部署不能安全启用凭证注入。兼容期内仍接受 default-allow 策略，但会发出安全警告，并应在未来收紧强制执行之前迁移到 defaultAction="deny"。

工作原理

Credential Vault 由 egress sidecar 实现。创建沙箱时必须同时提供出站 network_policy / networkPolicy，并启用 Credential Proxy。生命周期 API 字段名为 credentialProxy.enabled；各 SDK 按语言约定暴露该字段。

高层流程如下：

  1. 生命周期服务将 egress sidecar 挂到沙箱上。
  2. SDK 将凭证与绑定写入 sidecar 的 Credential Vault API。
  3. 沙箱进程以假值或空凭证环境变量运行。
  4. 沙箱发起 HTTPS 请求时，sidecar 中的透明 MITM 检查请求元数据。
  5. 若恰好有一个绑定匹配请求的 scheme、host、port、method 与 path，sidecar 会注入配置的认证头以及作用域内的占位符替换。
  6. 密钥值会从 vault 响应与响应头中脱敏。

当 active-vault 检查成功时，未匹配任何凭证绑定的请求会原样转发。凭证路径安全检查仅在绑定匹配且请求本将收到凭证之后才适用。active-vault 检查本身会在每次拦截流量选择绑定之前运行，包括那些本不会匹配任何绑定的主机请求。

MITM 进程使用的活跃 vault 通过 sidecar 内部的本地 Unix domain socket 提供。沙箱工作负载无法通过常规服务端代理路径获取该活跃状态。

每条新流量会有条件地使用缓存的不透明快照标签（在 If-None-Match 中）读取该私有端点。304 Not Modified 响应会复用同一份不可变的进程内快照，无需渲染或传输密钥值；200 OK 响应会携带一份完整校验过的替换快照以及新的不透明 ETag。成功的 create 与 patch 响应仅在存储已更改该标签后才确认，因此下一条流量能立即看到新凭证，而无需等待缓存 TTL。

该不透明标签与公开的 vault revision 相互独立。删除 vault 再创建可把公开 revision 重置为 1，但重建的 vault 会得到不同标签，无法复用已删除快照中的明文。404 Not Found 是私有端点的正常“无活跃 vault”结果：MITM 进程清空缓存快照，并在不注入凭证的情况下继续。

警告：运行时可用性依赖

私有 active-vault socket 是 Credential Proxy 拦截的所有流量的硬可用性依赖，而不仅是最终匹配到凭证绑定的流量。超时、连接拒绝、意外 EOF、5xx 响应、畸形快照或无效 ETag 都会清空受影响的明文缓存，并在任何上游转发之前以失败关闭请求。正文可安全缓冲的小请求会收到本地 503 Service Unavailable 响应。已在流式传输、可能越过流式阈值、或正文长度未知的请求则会直接终止，因为 mitmproxy 在流式开始后无法安全地合成本地响应。运维应将 sidecar 与私有 socket 作为 egress 数据面可用性的一部分进行监控。

跨暂停与恢复的持久性

警告：内存态

Credential Vault 条目是 egress sidecar 中的进程本地内存；它们不属于沙箱根文件系统或 BatchSandbox Pod 模板。Kubernetes 暂停会在快照后删除 Pod，因此恢复时新建的 egress sidecar 以空 vault 启动。在可信客户端再次创建凭证与绑定之前，凭证注入不会恢复。

请在沙箱外的可信控制面中保留原始 vault 请求或等价的密钥管理器引用。沙箱回到 Running 后，在允许依赖这些凭证的工作之前，再次调用 Credential Vault create API。不要把真实凭证值持久化到沙箱元数据、环境变量、快照或日志中。

Docker pause/unpause 会保留现有容器进程，但任何 egress sidecar 替换或重启也会创建新的内存 vault，并需要同样的重新注入流程。

服务网格兼容性

Credential Vault 依赖 egress sidecar 的透明重定向与 MITM 路径。若沙箱 Pod 还注入了 Istio/Envoy 等透明服务网格 sidecar，两层都会在同一网络命名空间中尝试拦截出站流量。OpenSandbox 目前不支持该组合用于 Credential Vault。

请改用以下运维模式之一：

  • 对需要 Credential Vault 的沙箱 Pod 禁用网格 sidecar 注入
  • 保留网格注入，但不要对这些 Pod 启用 credentialProxy / Credential Vault
  • 若必须注入网格，则将出站策略与凭证处理移到沙箱 Pod 之外的平台机制

关于底层 egress-sidecar 限制，参见 Egress。

凭证绑定有意设计得精确。需要 default-deny 出站策略。请使用窄路径匹配，例如 Anthropic API 调用使用 /v1/*。

认证类型

每个绑定使用一条 auth 规则，描述如何将引用的凭证渲染到出站请求中：

  • bearer：注入 Authorization: Bearer <credential>。
  • basic：注入 Authorization: Basic <credential>。凭证值必须已是 base64 编码的 username:password。
  • apiKey：将凭证值注入到配置的请求头名称中。
  • customHeaders：注入多个配置的请求头，每个头由各自的凭证支持。
  • passthrough：不注入认证头。当上游 API 需要路径、查询字符串或正文占位符中的凭证而非请求头时，与 substitutions 一起使用。

简单示例：

auth={"type": "bearer", "credential": "github-token"}
Authorization: Bearer <github-token>
auth={"type": "basic", "credential": "registry-basic"}
Authorization: Basic <base64(username:password)>
auth={"type": "apiKey", "name": "x-api-key", "credential": "anthropic-api-key"}
x-api-key: <anthropic-api-key>
auth={
    "type": "customHeaders",
    "headers": [
        {"name": "X-Client-Id", "credential": "client-id"},
        {"name": "X-Client-Secret", "credential": "client-secret"},
    ],
}
X-Client-Id: <client-id>
X-Client-Secret: <client-secret>

作用域占位符替换

某些上游 API 需要凭证出现在请求 URL 或正文中，而不是专用认证头。Credential Vault 可在不把真实凭证放入沙箱进程的情况下处理这些 API。所有认证类型都接受可选的 substitutions 列表。每条替换指定一个凭证、一个字面占位符，以及允许替换的请求面：

auth={
    "type": "passthrough",
    "substitutions": [
        {
            "credential": "client-secret",
            "placeholder": "__client_secret__",
            "in": ["body", "query"],
        }
    ],
}

当绑定仅执行替换且不应注入认证头时，使用 type="passthrough"。你也可以在同一上游请求既需要头注入又需要占位符替换时，将 substitutions 与 bearer、basic、apiKey 或 customHeaders 组合使用。

替换默认关闭，且为精确、字面、大小写敏感。仅重写已配置的面：

面（Surface）行为
path 在请求路径中替换占位符，并对凭证值做 URL 编码。若重写后的路径包含歧义路径段、编码分隔符或类似遍历的内容，sidecar 会拒绝请求，而不是把带密钥的 URL 转发到匹配作用域之外。
query 在查询字符串中替换占位符，并对凭证值做 URL 编码。
header 在原始请求头中替换占位符，排除 hop-by-hop 与安全敏感头，例如 Host、Content-Length 以及转发相关头。替换在 Credential Vault 注入认证头之前运行，因此 sidecar 不会重写它自己创建的凭证头。
body 在 UTF-8 请求正文中替换占位符。对于 application/json，替换按 JSON 字符串内容编码，因此请把占位符放在带引号的 JSON 字符串内。对于 application/x-www-form-urlencoded，替换会做表单编码。压缩与 multipart 正文会被跳过。

sidecar 对某个面的所有替换会在一份原始请求文本上一次完成。已插入的凭证值不会再被后续占位符扫描，从而防止一个密钥意外重写另一个密钥。当正文被重写时，sidecar 会更新 Content-Length 并移除 Transfer-Encoding，因为转发请求现在具有固定大小的缓冲正文。

占位符、原始凭证值、URL 编码值、表单编码值以及 JSON 转义值都会加入活跃脱敏集合。若绑定带有 substitutions、匹配了请求但未找到任何占位符，会发出 substitution-miss 日志且不暴露凭证值。

配置示例：

await sandbox.credential_vault.create(
    credentials=[
        Credential(name="tenant-id", source={"value": "tenant 42"}),
        Credential(name="api-key", source={"value": "query secret+value"}),
        Credential(name="client-secret", source={"value": 'body "secret" value'}),
    ],
    bindings=[
        CredentialBinding(
            name="token-request",
            match={
                "schemes": ["https"],
                "hosts": ["api.example.com"],
                "methods": ["POST"],
                "paths": ["/tenants/__tenant_id__/token"],
            },
            auth={
                "type": "passthrough",
                "substitutions": [
                    {
                        "credential": "tenant-id",
                        "placeholder": "__tenant_id__",
                        "in": ["path"],
                    },
                    {
                        "credential": "api-key",
                        "placeholder": "__api_key__",
                        "in": ["query"],
                    },
                    {
                        "credential": "client-secret",
                        "placeholder": "__client_secret__",
                        "in": ["body"],
                    },
                ],
            },
        )
    ],
)

沙箱可使用占位符代替真实密钥：

curl -X POST \
  "https://api.example.com/tenants/__tenant_id__/token?api_key=__api_key__" \
  -H "content-type: application/json" \
  --data '{"client_secret":"__client_secret__"}'

上游收到重写后的请求：

POST /tenants/tenant%2042/token?api_key=query%20secret%2Bvalue HTTP/1.1
content-type: application/json

{"client_secret":"body \"secret\" value"}

Egress Sidecar 配置

环境变量默认值说明
OPENSANDBOX_EGRESS_CREDENTIAL_VAULT_REQUIRE_TLS off 启用时（true/1/on），凭证保管库写操作（create、patch、delete）要求 TLS、回环传输，或来自已配置可信代理的 X-Forwarded-Proto: https。禁用时（默认），任何已认证请求无论传输方式都被接受。在无 TLS 终止反向代理、且 egress sidecar 可从不受信任网络直接到达的部署中启用此项。
OPENSANDBOX_EGRESS_CREDENTIAL_VAULT_TRUSTED_PROXY_CIDRS empty 允许断言 X-Forwarded-Proto: https 的逗号分隔 IP 地址或 CIDR。来自其他对等方的转发传输头会被忽略。当 TLS 在 egress sidecar 之前的反向代理处终止时配置此项。
OPENSANDBOX_EGRESS_CREDENTIAL_VAULT_REQUIRE_SCOPED_MATCH off 启用时，每个凭证绑定必须显式提供非空的 match.methods 与 match.paths，且路径不能包含主机级 /* 模式。省略任一字段的 vault create/patch 请求会被拒绝，而不是接收兼容性默认值。适用于将更高层 API 工具定义翻译为 Credential Vault 绑定的控制面。

scoped-match 设置是一个失败关闭（fail-closed）的集成防护。它不会从其他平台的 API 工具定义推断 method 或 path。创建 vault 的调用方仍须把预期的 method 与 path 复制到每个绑定中，并校验消毒后的绑定回读结果。

SDK 速查

所有沙箱 SDK 使用相同的线路契约。主要差异在于命名与语言风格：

SDK创建沙箱时启用代理Vault 入口Create / patch 方法
Python credential_proxy=CredentialProxyConfig(enabled=True) sandbox.credential_vault create(...)、patch(...)
Go CredentialProxy: &opensandbox.CredentialProxyConfig{Enabled: true} sandbox.CredentialVault(ctx) 或沙箱辅助方法 CreateCredentialVault(ctx, req)、PatchCredentialVault(ctx, req)
JavaScript/TypeScript credentialProxy: { enabled: true } sandbox.credentialVault create(request)、patch(request)
Kotlin/JVM .credentialProxyEnabled(true) 或 .credentialProxy { enabled(true) } sandbox.credentialVault() create(request)、patch(request)
C#/.NET CredentialProxy = new CredentialProxyConfig { Enabled = true } sandbox.CredentialVault 或沙箱辅助方法 CreateCredentialVaultAsync(...)、PatchCredentialVaultAsync(...)

vault API 返回消毒后的元数据。明文凭证值仅可写入，不会由 get、list 或 patch 响应返回。

Claude Code 与 Anthropic

本示例在沙箱中安装 Claude Code，并调用官方 Anthropic API 端点。真实 API key 在宿主机读取并写入 Credential Vault。沙箱仅看到假的 ANTHROPIC_API_KEY。

运行脚本前：

export ANTHROPIC_API_KEY="sk-ant-..."
# Optional: export ANTHROPIC_MODEL="<a Claude Code supported Anthropic model>"

运行：

import os
from datetime import timedelta

from opensandbox import SandboxSync
from opensandbox.models.sandboxes import (
    Credential,
    CredentialBinding,
    CredentialProxyConfig,
    NetworkPolicy,
    NetworkRule,
    SandboxImageSpec,
)


ANTHROPIC_HOST = "api.anthropic.com"
ANTHROPIC_BASE_URL = "https://api.anthropic.com"
REAL_API_KEY = os.environ["ANTHROPIC_API_KEY"]


sandbox_env = {
    "ANTHROPIC_BASE_URL": ANTHROPIC_BASE_URL,
    "ANTHROPIC_API_KEY": "fake-key-inside-sandbox",
}
if os.getenv("ANTHROPIC_MODEL"):
    sandbox_env["ANTHROPIC_MODEL"] = os.environ["ANTHROPIC_MODEL"]


sandbox = SandboxSync.create(
    image=SandboxImageSpec(
        os.getenv("SANDBOX_IMAGE", "opensandbox/code-interpreter:latest")
    ),
    timeout=timedelta(minutes=15),
    env=sandbox_env,
    network_policy=NetworkPolicy(
        defaultAction="deny",
        egress=[
            NetworkRule(action="allow", target=ANTHROPIC_HOST),
            NetworkRule(action="allow", target="registry.npmjs.org"),
        ],
    ),
    credential_proxy=CredentialProxyConfig(enabled=True),
)

try:
    sandbox.credential_vault.create(
        credentials=[
            Credential(
                name="anthropic-api-key",
                source={"value": REAL_API_KEY},
            )
        ],
        bindings=[
            CredentialBinding(
                name="anthropic-api",
                match={
                    "schemes": ["https"],
                    "hosts": [ANTHROPIC_HOST],
                    "methods": ["GET", "POST"],
                    "paths": ["/v1/*"],
                },
                auth={
                    "type": "apiKey",
                    "name": "x-api-key",
                    "credential": "anthropic-api-key",
                },
            )
        ],
    )

    sandbox.commands.run(
        "npm install -g @anthropic-ai/claude-code --no-audit --no-fund"
    )
    result = sandbox.commands.run("claude -p '1+1'")
    output = "".join(part.text for part in result.logs.stdout)
    print(output)
finally:
    sandbox.kill()
    sandbox.close()

Claude Code 进程从 ANTHROPIC_API_KEY 读取假密钥，但对 api.anthropic.com/v1/* 的出站 HTTPS 请求会从 Credential Vault 收到真实的 x-api-key 头。若环境使用私有 npm 镜像，请在网络策略与 npm install 命令中将 registry.npmjs.org 替换为该镜像主机。

使用 Vault 注入凭证的 Git 与 Curl

Credential Vault 也可保护 git 与 curl 等命令行工具使用的凭证。保持命令不含真实密钥，并将请求形态绑定到 Vault 中的凭证。

对于私有 Git 仓库，存储 base64 编码的 username:token 值，并以 basic auth 绑定：

Credential(name="git-basic", source={"value": "<base64(username:token)>"})

CredentialBinding(
    name="git-basic",
    match={
        "schemes": ["https"],
        "hosts": ["git.example.com"],
        "paths": ["/org/private-repo.git*"],
    },
    auth={"type": "basic", "credential": "git-basic"},
)

然后运行不含嵌入凭证的普通 URL：

GIT_TERMINAL_PROMPT=0 git clone https://git.example.com/org/private-repo.git

对于期望令牌头的 API 请求，将路径与方法绑定到 apiKey auth 规则：

Credential(name="api-token", source={"value": "<token>"})

CredentialBinding(
    name="api-token",
    match={
        "schemes": ["https"],
        "hosts": ["api.example.com"],
        "methods": ["GET"],
        "paths": ["/v1/projects/123/variables"],
    },
    auth={"type": "apiKey", "name": "PRIVATE-TOKEN", "credential": "api-token"},
)

沙箱命令保持无密钥：

curl -fsS https://api.example.com/v1/projects/123/variables

绑定建议

  • 使用 defaultAction="deny"，并仅允许工具所需的服务主机。default-allow 策略已弃用，因其可能允许凭证目标绕过，并将发出安全警告。
  • 尽可能按路径限定绑定范围，例如 /v1/*。
  • 避免在同一优先级上出现重叠绑定；歧义匹配会被拒绝。
  • 被拒绝的请求（歧义路径、跨越绑定边界的编码分隔符）在请求正文较小且完全已知时返回 403。正文超过 mitmproxy 流式阈值（约 1 MiB）或长度未知（chunked）的请求在正文流式传输期间无法以 403 应答，因此 sidecar 会改为断开连接——无论哪种方式，请求都不会被转发到上游。
  • 不要把真实密钥放进沙箱 env、命令参数、文件或元数据中。
  • 当 CLI 拒绝在无密钥时启动时，保留假环境变量；认证出站请求的是 vault 注入的请求头。

从 ports 迁移

match.ports 字段已弃用。端口现在由 scheme 推导（https→443，http→80）。仅支持端口 80 与 443；非标准值会以校验错误拒绝。

若现有绑定使用 ports 收窄作用域，请迁移到等价的 schemes 限制：

之前之后
schemes: ["http", "https"], ports: [443] schemes: ["https"]
schemes: ["http", "https"], ports: [80] schemes: ["http"]
schemes: ["https"], ports: [443] schemes: ["https"]（移除 ports）
